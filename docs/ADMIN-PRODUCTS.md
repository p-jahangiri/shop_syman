# مدیریت صفحه‌بندی‌شدهٔ کالا و انتخاب‌گر محتوا

پذیرش تازه 2026-10-23: SQL۱۲۹ و۱۷ QA محصول/سریال پیشین موفق‌اند؛ انتخاب‌گر CMS نیز در هفت بررسی متصل انتخاب دو کالا/ترتیب/جست‌وجوی SKU/حفظ انتخاب خارج نتیجه و ذخیره/بازخوانی پیش‌نویس را پذیرفت. محتوای عمومی پیش از انتشار تغییر نکرد؛ publication/rollback پس از رد auto-review منتظر پاسخ اجازهٔ محدود مالک است. CSS فاصله‌های تو‌در‌توی CMS/mobile اصلاح و build/typecheck مستقل موفق شد؛ تصویر پس از اصلاح باقی. [CUSTOMER-OPERATIONS-QA](CUSTOMER-OPERATIONS-QA.md) وضعیت تازه و حدود را دارد؛ عبارت‌های compile-only زیر تاریخی‌اند.

پذیرش جدید 2026-10-23: D20 توقف فضا را رفع کرد؛ **۱۲۹/۱۲۹ SQL واقعی** شامل آزمون‌های این برش موفق شدند. اعداد compile-only و توقف D19 متن زیر تاریخی‌اند؛ QA مرورگر متصل، main migration۱۸–۲۱ و Linux x64/بار هنوز جدا باقی‌اند. وضعیت جاری در [STATUS](STATUS.md) است.

وضعیت 2026-10-23: سورس، build/unit/contract و QA محدود رابط آماده‌اند. SQL جدید، ویرایش/انتشار واقعی با MFA، ذخیرهٔ CMS و انتشار روی اجرای اصلی هنوز باقی‌اند. کل پروژه و همهٔ pagination مدیریت کامل نشده‌اند.

## قرارداد و داده

| مسیر `/api/admin` | رفتار و مجوز |
|---|---|
| GET `products?query=...&status=all&categoryId=...&brandId=...&cursor=...` | catalog.read کامل؛ schemaVersion1/pageSize50/items/nextCursor |
| GET `products/{id}` | catalog.read کامل؛ schemaVersion1/product، جزئیات همان کالا یا404 |
| GET `catalog/product-lookup?ids=id1&ids=id2` | catalog.read کامل؛ حداکثر۲۴ شناسهٔ یکتا، فقط خلاصهٔ موجودها |
| GET `catalog?metadataOnly=true` | catalog.read کامل؛ دسته/برند/ویژگی/گزینه‌ها مانند قبل، products خالی و بدون query graph کالا |

GET قدیمی catalog بدون flag، برای سازگاری همچنان graph کامل می‌دهد. پنل جاری همیشه metadataOnly=true می‌فرستد و هیچ مصرف‌کنندهٔ runtime آن به data.products متکی نیست. دسته‌ها/برندها/تعریف‌ها/گزینه‌ها و طرح‌های خرید هنوز کامل خوانده می‌شوند؛ این بخش‌ها تکمیل pagination/انتخاب‌گر لازم دارند. خطای API با fixture یا graph قدیمی جایگزین نمی‌شود.

خلاصه شامل id/slug، نام دو زبان، دسته/برند، وضعیت، featured و تعداد تمام تنوع‌هاست؛ قیمت، گارانتی، تصویر، توضیح و موجودی در query فهرست/lookup انتخاب نمی‌شوند. Draft/Hidden، انتشار آینده و تنوع غیرفعال عمداً برای مدیریت حفظ می‌شوند. query تا۱۲۰ نویسه/۸ واژه با نرمال‌سازی فارسی و AND واژه‌ها در نام دو زبان یا SKU، status برابر all/Draft/Published/Hidden و شناسه‌های امن دسته/برند است. فیلترِ فعالیت عمومی فروشگاه یا موجودی به این مسیر افزوده نشده است. فیلدهای جست‌وجوی تعمیرنشده503 می‌دهند.

ترتیب شناسه صعودی و seek با همان collation SQL است؛ TOP51 فقط وجود صفحهٔ بعد را مشخص می‌کند. cursor حداکثر۳۰۰ نویسه و وابسته به تمام فیلترهای نرمال‌شده است؛ نامعتبر یا مربوط به فیلتر دیگر400 می‌شود. binding مجوز یا امضای امنیتی نیست. lookup GET است و transaction/audit مربوط به mutation را آغاز نمی‌کند؛ نام آن در زیر catalog قرار دارد تا شناسهٔ معتبر «lookup» با مسیر جزئیات کالا تداخل نکند. policy، نه cursor، مرجع دسترسی است؛ mfa_pending و catalog.write تنها کافی نیستند.

جزئیات از graph مشترکِ Catalog با فیلتر شناسه، no-tracking و split query خوانده می‌شود؛ فقط یک کالا، ولی **تمام** رابطه‌های قابل ویرایش آن دریافت می‌شوند و تنوع‌ها بی‌صدا بریده نمی‌شوند. DTO صریح شامل version کالا/تنوع، ترجمه‌ها، ویژگی تایپ‌دار و selections، همهٔ تنوع‌های فعال/غیرفعال، رسانهٔ مرتب، روش خرید و طرح چک است. SearchName/SearchSku، price history و فیلدهای غیرقابل ویرایش فرم فعلی منتشر نمی‌شوند. priceRial/compareAtPriceRial رشتهٔ صحیح ریال‌اند؛ تبدیل Number برای پول انجام نمی‌شود. مسیر عمومی فروشگاه از همان graph با فیلترهای قبلی استفاده می‌کند؛ آن رفتار تغییر نکرد.

خلاصهٔ صفحه bounded است؛ جزئیات یک کالا تمام روابطش را نگه می‌دارد و سقف کلی برای روابط انباشتهٔ قدیمی اضافه نشده است. محدودیت ورودی فرمان‌ها، مدیریت تعداد زیاد تنوع و سنجش بار/plan همچنان باید بررسی شوند. خواندن‌ها snapshot مشترک تراکنشی ندارند؛ تغییر همزمان نام/وضعیت می‌تواند پیمایش را تغییر دهد. mutation همچنان نسخه، اعتبارسنجی، تراکنش/audit و snapshot مالی قبلی را اعمال می‌کند؛ خواندن تازه جای آن‌ها را نمی‌گیرد. schema تغییر نکرده و Catalog/Inventory model check بدون تغییر جامانده است.

## پنل

ProductsPage با صفحهٔ۵۰، فیلتر نام/SKU/وضعیت/دسته/برند، قبلی/بعدی، reset، خالی/خطا/retry، جای جدول کامل حافظه‌ای را گرفت. فرم موجود ProductForm حفظ شد و فقط هنگام ویرایش، جزئیات تازهٔ همان کالا را می‌گیرد؛ پاسخ ناسازگار یا شناسهٔ متفاوت فرم را باز نمی‌کند. ورودی قیمت بزرگ، false/zero، selections و تنوع غیرفعال حفظ می‌شوند. ترجمهٔ واقعاً مفقود به فیلد خالی قابل تکمیل تبدیل می‌شود؛ محتوای ترجمه اختراع نمی‌شود. آرایهٔ رسانهٔ cache برای مرتب‌سازی درجا تغییر نمی‌کند. refetch خودکار هنگام focus/reconnect برای جزئیات خاموش است تا draft با تعویض ناخواستهٔ نسخه پاک نشود؛ پس از تعارض باید دادهٔ تازه بررسی شود.

ProductPicker در بلوک‌های products/collection از صفحه‌های خلاصه و lookup همان شناسه‌های منتخب استفاده می‌کند. تا بازکردن انتخاب‌گر query آن فعال نیست. انتخاب‌های خارج صفحه یا ناموجود و ترتیبشان حفظ می‌شوند؛ حذف فقط صریح است و بالا/پایین ترتیب را تغییر می‌دهد. حداکثر۲۴ انتخاب موجود در قرارداد CMS در UI هم رعایت می‌شود؛ در سقف، انتخاب جدید غیرفعال و حذف انتخاب قبلی ممکن است. خطای lookup شناسه‌ها را حذف نمی‌کند و retry دارد. تغییرات این fixture فقط state محلی آزمایشی‌اند؛ ذخیرهٔ واقعی CMS هنوز باید پذیرفته شود.

## اصلاح سازگاری JSON و شواهد

تنظیم واقعی ASP.NET، nullها را به‌صورت پیش‌فرض حذف می‌کند. بررسی این برش نشان داد nextCursor نهایی در صفحهٔ کالا/موجودی/گردش و version تنوع بدون Stock باید **صریحاً null** باشند تا قرارداد strict پنل درست بماند. این propertyها JsonIgnoreCondition.Never دارند؛ تنظیم عمومی JSON و پاسخ‌های قدیمی دیگر تغییر نکردند. تست HTTP واقعیِ داخل test host وجود property و نوع null را بررسی می‌کند.

- **۲۸۸ بک‌اند موفق**، شامل۲۱ مورد تازهٔ فیلتر/cursor، SQL مختصر، graph تک‌کالا، همهٔ روابط و پول بزرگ، policy/MFA، lookup بدون mutation و شناسهٔ رزروشدهٔ lookup؛ تست‌های قبلی موجودی/گردش نیز شکل واقعی JSON را بررسی می‌کنند.
- **۱۶ contract پنل موفق**، شامل۶ مورد تازهٔ صفحه/فیلتر/انتخاب/جزئیات، پول بزرگ، نسخه/شناسه، false/zero و حفظ locale. TypeScript و Vite build ایزولهٔ `tmp/admin-products-dist` موفق‌اند؛ entry۴۰۶٫۰۰kB/gzip۱۲۵٫۴۶، products۵٫۸۰، contract۳٫۶۸ و operations۲۶٫۶۴kB. هشدار۵۰۰kB و تغییر threshold وجود ندارد؛ این اعداد Core Web Vitals نیستند.
- **۷ بررسی ASP.NET→TypeScript**: پاسخ HTTP واقعی ApiFactory با readerهای مصنوعی فقط داخل test assembly، از serializer و middleware واقعی، با schemaهای production پنل parse شد؛ money/false/zero و nullهای صریح حفظ شدند. capture فقط با env صریح SHOP_ADMIN_CONTRACT_CAPTURE_DIR فعال است؛ `scripts/verification/verify-admin-wire.mts artifacts/checks/admin-wire-final` مرجع و report.json نتیجه است. این شاهد SQL یا احراز هویت واقعی نیست و credential تولید نمی‌کند.
- **۲۳ QA محدود رابط** روی ProductsPage/ProductPicker واقعی با fixture صریح فقط خواندنی:۵۰/۵۰/۱، فیلتر ترکیبی، SKU خارج صفحه، خطا/retry/رد schema، نگهداری انتخاب مفقود/خارج صفحه، ترتیب/حذف صریح، lookup503، سقف۲۴ و جست‌وجو/بستن بدون حذف؛ فهرست و picker در۳۹۰×۸۴۴ بدون overflow سند. smoke نهایی اتصال مسیر جدید lookup را هم تأیید کرد. console error/warning گزارش‌شده صفر؛ فرم ویرایش/ذخیرهٔ CMS/ورود واقعی آزموده نشدند.
- `serve-admin-products-layout.py --explicit-readonly-fixture` فقط دادهٔ واضح نمونه، GET metadata و state محلی دارد؛ درخواست نوشتن و خواندن snapshot کامل در هر دو اجرای QA صفر بود؛ Authorization صفر، اما۴۹ درخواست cookie موجود مرورگر روی loopback داشتند. فقط boolean حضور ثبت شد، مقدار cookie لاگ نشد و fixture آن را برای هویت به کار نمی‌برد؛ پذیرش ورود از این شاهد حاصل نمی‌شود. parent/child خود QA terminal، پورت۳۱۷۵/۵۱۸۱ بسته، control/پوشهٔ موقت حذف، viewport reset و تب‌های۱۹/۲۰ بسته شدند. گزارش/تصاویر admin-products-* و sayman-admin-products-{desktop,mobile,picker}.jpg در artifacts/checks هستند؛ dist اصلی تغییر نکرد.

دو SQL تازه برای۱۰۱ کالا/۳۰۳ تنوع با Draft/Hidden/غیرفعال، صفحه/lookup/تمام روابط/پول بزرگ، metadataOnly و سازگاری legacy، MFA نقش واقعی، GET بدون audit و ویرایش نسخه‌دار/409 نوشته و فقط compile شده‌اند. discovery بدون اجرا۷۳ مورد را نشان داد؛ شاهد SQL قبلی۵۹ و۱۴ مورد تازه هنوز اجرا نشده‌اند. طبق D19 تا اعلام پایان آزادسازی فضا SQL/Docker تازه اجرا نشود؛ سپس SQL۷۳، QA واقعی ویرایش/انتشار/انتخاب CMS و migration۱۸/build/update/smoke اصلی ادامه یابد. providerها غیرفعال و parseh-chat-redis خاموش بمانند؛ این برش پایان پروژه نیست.

نقطهٔ ادامهٔ فعلی پس از برش STAFF-ADMINISTRATION: هدف SQL۸۴ با۲۵ مورد تازهٔ اجرا‌نشده است؛ شش مورد کارکنان به مجموعه افزوده شده و migration۱۹ Identity نیز کنار۱۸ Sales قبل از runtime تازه لازم است. اعداد discovery بالای این سند شاهد زمان همان برش‌اند؛ دستور اجرای جاری در [STATUS.md](STATUS.md) و [MFA-RECOVERY.md](MFA-RECOVERY.md) دنبال شود. تا اعلام مالک دربارهٔ فضا SQL/Docker تازه اجرا نشود.
