# سفارش موقت و اتصال رزرو

پذیرش مرورگر تازه 2026-10-23: quote3، ثبت فیزیکی/دیجیتال، سبد خالی، snapshot دقیق، فهرست FA/EN، لغو مشتری و مدیر و آزادسازی رزرو بدون کاهش OnHand در SQL واقعی موفق‌اند؛ جزئی از۴۷ بررسی [CUSTOMER-OPERATIONS-QA](CUSTOMER-OPERATIONS-QA.md). D21 تنظیمات نمونه را فقط در QA اجازه داد؛ سیاست اصلی تغییر نکرد. mobile مشتری/قطع پاسخ/worker این run و پرداخت واقعی پذیرفته نشده‌اند. تاریخچهٔ انتظار فضا/QA زیر جاری نیست؛ اصلی۱۷/source۲۱ و مهاجرت اصلی معوق‌اند.

پذیرش جدید 2026-10-23: D20 توقف فضا را رفع کرد؛ **۱۲۹/۱۲۹ SQL واقعی** شامل آزمون‌های این برش موفق شدند. اعداد compile-only و توقف D19 متن زیر تاریخی‌اند؛ QA مرورگر متصل، main migration۱۸–۲۱ و Linux x64/بار هنوز جدا باقی‌اند. وضعیت جاری در [STATUS](STATUS.md) است.

وضعیت 2026-10-23: بک‌اند و رابط‌های این برش در سورس پیاده‌اند؛ پذیرش متصل رابط و انتشار روی اجرای اصلی هنوز انجام نشده است. پس از پاسخ D19، اجرای تازهٔ SQL/Docker و migration اصلی منتظر اعلام پایان آزادسازی فضاست. این برش خرید نهایی یا اتصال درگاه نیست.

## رفتار و تنظیمات

Sales مالک `CheckoutOrderSettings`، `Orders`، `OrderLines` و `OrderEvents` است. نبود رکورد تنظیم یعنی سفارش موقت غیرفعال؛ خواندن رکوردی ایجاد نمی‌کند. مدیر دارای `sales.write` و MFA می‌تواند فعال‌سازی، مهلت رزرو ۱–۶۰ دقیقه و سقف سفارش باز هر مشتری ۱–۱۰ را با rowversion و audit اتمیک تنظیم کند. پیش‌فرض فنی ۱۵ دقیقه/یک سفارش است و سیاست تجاری تأییدشده نیست (A15).

فقط روش نقدی `online` فعال و بدون نیاز به تأیید، مبلغ نهایی مثبت و هزینه‌های معلوم اجازهٔ سفارش موقت دارند. گردش چکی، اقساط ارائه‌دهنده و مبلغ صفر فعلاً مجاز نیستند. درگاه غیرفعال مانع ساخت سفارش موقتِ صریحاً فعال‌شده نیست، ولی `canPay:false` و `gateway_unconfigured` همواره حفظ می‌شوند. مسیر Paid، callback، قطعی‌کردن خرید یا ارسال کالا در این برش وجود ندارد.

quote تازه schema3 است؛ نسخهٔ قیمت هر قلم و گزینهٔ `temporaryOrder` را دارد. `canPlaceOrder` برای پرداخت نهایی همچنان false است. replay نسخه‌های۱/۲ خوانده می‌شود ولی فقط quote تازهٔ۳ امکان سفارش دارد. محاسبهٔ quote موجودی رزرو نمی‌کند؛ ثبت سفارش دوباره مالک، مهلت، نسخهٔ سبد، قیمت/شرایط، تنظیم سفارش/هزینه و موجودی را بررسی می‌کند.

## اتمیک بودن و تکرار

composition root، contextهای Sales/Catalog/Inventory/Payments/Credit همان فرمان را به یک connection و transaction SQL با isolation برابر Serializable متصل می‌کند. قفل ثابت مالک، قفل انحصاری سبد و قفل‌های قرارداد موجودی رعایت می‌شوند؛ ماژول‌ها از DbContext یکدیگر استفاده نمی‌کنند. سفارش و اقلام/event، رزرو و خالی‌کردن سبد با هم commit یا rollback می‌شوند. شکست SQL پس از hold هیچ رزرو یا سفارش نیمه‌کاره‌ای باقی نمی‌گذارد.

کلید تکرار `(OwnerId, RequestId)` همراه hash ورودی نرمال‌شده ذخیره می‌شود. تکرار همان payload همان سفارش و مهلت ثابت را برمی‌گرداند؛ payload متفاوت409 است. هر quote تنها یک سفارش دارد؛ عوض‌کردن requestId به ایجاد سفارش دوم منجر نمی‌شود. snapshot نام/تنوع/SKU/گارانتی/قیمت و تمام مبالغ صحیح ریال پس از ثبت از کاتالوگ جاری تغییر نمی‌کنند. شمارهٔ مرجع از identity bigint سرور ساخته و به صورت `SM-…` رشته‌ای ارائه می‌شود.

لغو فقط سفارش پرداخت‌نشده را با rowversion آزاد می‌کند؛ تکرار لغو/انقضا دوباره موجودی آزاد نمی‌کند. OnHand و دفتر خروج فیزیکی در لغو تغییر نمی‌کنند. worker دقیقه‌ای حداکثر۱۰۰ مورد را با scope و transaction مستقل برای هر سفارش پردازش می‌کند؛ شکست یک مورد جلوی بقیه را نمی‌گیرد. فرمان `--expire-orders` از همین runner استفاده می‌کند. خواندن پس از مهلت فوراً وضعیت مؤثر Expired و عدم امکان پرداخت/لغو را نشان می‌دهد، حتی اگر worker هنوز نرسیده باشد. انقضا یا آزادسازی زودتر توسط worker موجودی نیز قابل تکرار است.

## API و حریم خصوصی

| مسیر | ورودی / دسترسی |
|---|---|
| `POST /api/orders` | مشتری تأییدشده؛ quoteId، UUID درخواست، نام/موبایل، delivery در صورت فیزیکی بودن، یادداشت و acknowledgeTemporary=true؛ مبلغ/مالک از ورودی تعیین نمی‌شوند |
| `GET /api/orders?cursor=…` | فقط سفارش‌های همان مشتری؛ seek pagination بیست‌تایی با CreatedAt/Id؛ بدون نشانی، تلفن و OwnerId |
| `GET /api/orders/{id}` | جزئیات خصوصی سفارش خود مشتری |
| `POST /api/orders/{id}/cancel` | همان مالک، version؛ transaction مشترک Sales/Inventory |
| `GET/PUT /api/admin/order-settings` | sales.read/write؛ نوشتن با MFA، نسخه و audit |
| `GET /api/admin/orders?cursor=…` | sales.read؛ summary بدون تماس/نشانی، دارای OwnerId برای مسیر مدیریت |
| `GET /api/admin/orders/{ownerId}/{id}` | sales.write؛ جزئیات خصوصی مورد نیاز عملیات |
| `POST /api/admin/orders/{id}/cancel` | sales.write، ownerId/version؛ تغییر سفارش/رزرو و audit اتمیک |

نقش SalesManager مجوز sales.read/write دارد؛ FinanceManager فقط sales.read دارد؛ نقش‌های مدیریتی همچنان MFA کامل لازم دارند. Origin روی mutation و GET دارای Origin بررسی می‌شود؛ customer group محدودیت۳۰ درخواست در دقیقه برای هر هویت دارد. فهرست۲۰+۱ و cursor محدود۲۰۰کاراکتری است؛ offset و بارگیری همهٔ سفارش‌ها وجود ندارد.

نشانی اولیه فقط ایران است؛ صرفاً دیجیتال delivery ندارد و ارسال فیزیکی صفر است. موبایل فارسی/عربی و +98/0098 به `09…` نرمال می‌شود؛ کدپستی ده‌رقمی لازم است. تأیید مالکیت موبایل/دفتر نشانی جدا هنوز پیاده نشده و شمارهٔ تماس به معنی هویت تأییدشدهٔ تلفنی نیست. نام، یادداشت و نشانی حدود مشخص دارند؛ دادهٔ واقعی مشتری در fixture یا گزارش آزمون نوشته نمی‌شود.

BFF Next فقط عملیات و مسیرهای مشخص را می‌پذیرد؛ body تا۱۶KiB، پاسخ تا۱MiB، مهلت۱۲ثانیه و cancellation درخواست دارد. فقط bearer و headerهای صریح storefront ارسال می‌شوند؛ cookie، header مدیریت، Location و Set-Cookie upstream عبور نمی‌کنند. schema و تطابق quote/id پاسخ کنترل می‌شود؛ خطا فقط code دارد. تمام پاسخ‌ها private/no-store/noindex هستند. PWA مسیرهای سفارش و API را cache نمی‌کند. توکن و اطلاعات فرم فقط در حافظه‌اند؛ تغییر هویت دادهٔ خصوصی صفحه را کنار می‌گذارد، از جمله پاسخ دیررس پس از retry احراز هویت.

## رابط‌ها

فروشگاه FA/EN: ورود با returnTo محدود به checkout/orders، فرم تماس/نشانی مشروط، رضایت صریح سفارش پرداخت‌نشده، نگه‌داشتن payload و UUID یکسان هنگام نتیجهٔ نامعلوم، پیوند بررسی سفارش‌ها، فهرست صفحه‌بندی‌شده، جزئیات snapshot و لغو با تأیید. پس از ثبت، مقصد صفحهٔ همان سفارش است. پاسخ نامعلوم موفقیت فرض نمی‌شود؛ پس از reload باید فهرست سفارش‌ها بررسی شود. هیچ دادهٔ فرم یا مبلغ جدیدی در localStorage ذخیره نمی‌شود.

پنل مستقل: صفحهٔ lazy سفارش‌ها و تنظیم رزرو، summary بیست‌تایی و جزئیات/لغو مجوزدار. خطای نسخه باید با خواندن وضعیت تازه حل شود؛ فرم تنظیمات در خطا بسته نمی‌شود. صفحهٔ مهمان/خطا در مرورگر پذیرفته شد؛ فرم مشتری واردشده و عملیات مدیر هنوز به SQL/MFA واقعی نیاز دارند. وجود JSX یا موفقیت typecheck جای آن QA نیست.

## شواهد و کارهای باقی

- اجرای تازهٔ سبک: **۹۱ تست فروشگاه،۱۹۴ تست بک‌اند در آخرین اجرا** موفق؛ typecheck فروشگاه/پنل موفق. build پروژه‌های SqlTests و UiHarness با صفر warning/error؛ فقط compile بوده و اتصال SQL نداشته است. Next در `.next-qa` و Vite در `tmp/orders-admin-dist` جدا از خروجی زنده build شدند. entry پنل۵۱۳٫۱۰→۴۰۲٫۰۱kB و هشدار قبلی رفع شد؛ ADMIN-PERFORMANCE دامنهٔ سنجش را شرح می‌دهد. دو تست runtime پنل تازه هم موفق‌اند.
- SQL ثبت‌شدهٔ پیش از توقف این ادامه: **۵۹ موفق**، شامل۱۲ مورد سفارش (snapshot مبلغ بزرگ، replay همزمان، آخرین واحد، تغییر قیمت/تنظیم/سبد، مالکیت، rollback بعد از hold، لغو همزمان، دو worker انقضا، دیجیتال/فیزیکی و سقف سفارش باز). `sql-tests.log` مرجع همان اجراست.
- چهار مورد تازهٔ SQL سفارش (غیرفعال‌سازی و quote منقضی، rollback لغو مدیر هنگام شکست audit، seek pagination بیست‌ویک سفارش) اضافه و compile شده‌اند؛ **هنوز اجرا نشده‌اند**. دو projection آفلاین، دو sitemap، دو history انبار، دو stock page و دو admin products SQL تازه نیز در برش‌های بعد اضافه شده‌اند؛ مجموعهٔ بعدی۷۳ است و هنوز اجرا نشده.
- migration هجدهم `20261022211322_TemporaryOrders` و SQL idempotent تازه در `backend/sql/sales.sql` آماده‌اند؛ model check تغییر جامانده ندارد. **روی Sayman اصلی اعمال نشده** و اجرای زنده همچنان برش هزینه با schema2/هفده migration است.
- اولین اجرای کامل قبلی یک SIGSEGV در CoreCLR/GetThreadLocalStaticBase داشت؛ علت قطعی نشده است. سپس۱۲ سفارش به‌تنهایی و۵۹ تست کامل بدون حذف همزمانی موفق شدند. پذیرش نهایی Linux x64 جدید هنوز وجود ندارد؛ crash را به OOM نسبت ندهید. امکان orphan دیتابیس/key تستِ همان اجرای crash باید با شواهد مالکیت دقیق بررسی شود؛ پاک‌سازی عمومی SaymanTest_* مجاز نیست.
- ۱۱ بررسی محدود مرورگر مهمان/خطا و۱۴ HTTP مرز BFF روی build تازهٔ Next موفق‌اند؛ source/API جدید در build ایزوله اجرا شد. fixture فقط metadata عمومی و401/503 داشت و هیچ ورود/سفارش موفقی نمی‌ساخت. تست واقعی از پنل/MFA موقت تا quote3، ثبت، فهرست، لغو و FA/EN/موبایل؛ smoke BFF→SQL؛ build عادی/migration اصلی و update runtime پس از اعلام فضا باقی‌اند. harness فقط در پروژهٔ تست با `SHOP_UI_OPERATIONS_QA=1` مدیر موقتِ ازپیش دارای MFA می‌سازد؛ هرگز از حساب یا enrollment مالک استفاده نمی‌کند. `SHOP_UI_FINANCE_QA=1` همچنان FinanceManager محدود می‌سازد. اجرا، credential و کلید/DB همان harness باید در پایان پاک شوند.
- gateway/SMS/email D16، نرخ/قواعد واقعی، آدرس وابسته به ارسال/وزن، تخفیف، تأیید چک، پرداخت دیررس، تخصیص/خروج، برگشت/مرجوعی و سیاست نگهداری PII/quote هنوز بازند. هیچ‌کدام با سفارش موقت کامل تلقی نمی‌شوند.

اسکریپت‌های QA بدون SQL: `build-storefront-isolated.py`، `serve-storefront-isolated.py api`، `serve-orders-layout-fixture.py --explicit-layout-fixture` و `smoke-orders-bff-unauthenticated.py`. fixture باید صریح و فقط برای guest/layout باشد؛ ابتدا شرط ادامهٔ D19 را برای harness واقعی رعایت کنید. این سه سرویس موقت بسته و فایل کنترل fixture پاک شدند؛ تصویر/گزارش در orders-layout-ui ثبت است.

پس از اعلام پایان آزادسازی: سلامت/فضا را فقط بخوانید؛ SQL۷۳ را اجرا و نتیجه را ثبت کنید، سپس QA ایزوله و migration/update اصلی را انجام دهید. ساخت Docker تنها با guard حداقل۱۰GiB شروع شود. parseh-chat-redis خاموش بماند و volume/فایل شخصی حذف نشود.

نقطهٔ ادامهٔ فعلی پس از برش STAFF-ADMINISTRATION: هدف SQL۸۴ با۲۵ مورد تازهٔ اجرا‌نشده است؛ شش مورد کارکنان به مجموعه افزوده شده و migration۱۹ Identity نیز کنار۱۸ Sales قبل از runtime تازه لازم است. اعداد discovery بالای این سند شاهد زمان همان برش‌اند؛ دستور اجرای جاری در [STATUS.md](STATUS.md) و [MFA-RECOVERY.md](MFA-RECOVERY.md) دنبال شود. تا اعلام مالک دربارهٔ فضا SQL/Docker تازه اجرا نشود.
