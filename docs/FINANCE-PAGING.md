# فهرست و ویرایش شرایط خرید در پنل

در D87 از فرم روش و طرح، ابتدا خلاصهٔ مبلغ ریالی، وضعیت، دسته و شرایط مرتبط را بازبینی کنید و سپس ذخیره را تأیید کنید. نرخ‌های طرح در فرم به درصد و حداکثر دو رقم اعشار وارد می‌شوند؛ سرور همچنان مقدار صحیح basis point و نسخهٔ مورد انتظار را دریافت می‌کند. پاسخ نامشخص نیازمند بازخوانی فهرست است. مرحلهٔ بازبینی جای کنترل مجوز و نسخه در سرور را نمی‌گیرد. مرجع طراحی: [راهنمای مجوز عملیات OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html).

پذیرش جدید 2026-10-23: D20 توقف فضا را رفع کرد؛ **۱۲۹/۱۲۹ SQL واقعی** شامل آزمون‌های این برش موفق شدند. اعداد compile-only و توقف D19 متن زیر تاریخی‌اند؛ QA مرورگر متصل، main migration۱۸–۲۱ و Linux x64/بار هنوز جدا باقی‌اند. وضعیت جاری در [STATUS](STATUS.md) است.

وضعیت 2026-10-23: سورس و آزمون مستقل آماده؛ پذیرش SQL/MFA و ذخیرهٔ متصل هنوز باقی است. D19 همچنان منتظر اعلام پایان آزادسازی فضاست. در این برش SQL/Docker، migration اصلی، runtime اصلی و Redis چت تغییر نکردند. migration تازه‌ای لازم نیست؛ سورس۲۰ و اصلی۱۷ است و۱۸/۱۹/۲۰ مربوط به برش‌های قبلی همچنان اعمال نشده‌اند.

## مسئله و رفتار تازه

FinancePage قبلاً تمام روش‌ها/طرح‌ها و محدودیت دستهٔ تک‌تک آن‌ها را می‌خواند و سپس در مرورگر فیلتر و صفحه‌بندی می‌کرد. داشبورد هم برای شمردن طرح فعال کل آرایه را می‌گرفت. اکنون هر فهرست حداکثر۵۰ خلاصه می‌گیرد؛ جزئیات همان روش/طرح هنگام بازکردن خوانده می‌شود. شمارندهٔ داشبورد query مستقل دارد. قرارداد عمومی مشتری و خواندن legacy برای انتخاب روش/طرح در ویرایش کالا در این برش محدود یا قطع نشده‌اند.

GETهای تازه همگی finance.read کامل، token_kind=access و سیاست‌های همان گروه admin را می‌خواهند؛ مهمان، MFA ناتمام یا cms.read کافی نیست. این GETها وارد transaction/audit فرمان نمی‌شوند:

- `/api/admin/purchase-methods-page?query=&enabled=all&kind=all&categoryId=...&cursor=...`
- `/api/admin/cheque-plans-page?query=&enabled=all&categoryId=...&cursor=...`
- `/api/admin/purchase-methods/{id}` و `/api/admin/cheque-plans/{id}`
- `/api/admin/purchase-summary`

صفحه schemaVersion=1/pageSize=50/items/nextCursor دارد؛ null آخرین cursor صریح serialize می‌شود. query حداکثر۱۲۰ نویسه/۸ واژه، enabled فقط all/true/false و kind فقط all/online/cheque/installment است. kind برای طرح چک وجود ندارد. query تکراری/ناشناخته، شناسهٔ غیر ASCII مجاز، cursor خراب/بیش از۵۱۲ نویسه یا متعلق به scope/فیلتر دیگر پیش از reader رد می‌شوند. Id طول۱–۶۴ و حروف/رقم لاتین/خط تیره/زیرخط دارد. cursor seek بر Id صعودی و SHA256 فیلتر نرمال‌شده و scope روش/طرح تکیه دارد؛ امضای مجوز یا snapshot ماندگار نیست.

Search روی نام فارسی/انگلیسی/شناسه، با نرمال‌سازی ورودی ی/ک/ارقام/نیم‌فاصله/اعراب و replacement/CI_AI در query است. SQL translation آزموده شد؛ صحت جست‌وجوی فارسی روی SQL، plan و بار هنوز پذیرفته نشده‌اند. فیلتر «قابل استفاده برای دسته» موارد بدون محدودیت دسته را هم شامل می‌شود؛ این معنا در پنل نوشته شده است. query ابتدا TOP51 متادیتا را می‌گیرد، سپس۵۰ آیتم و cursor می‌سازد؛ graph دسته، توضیح، مبلغ یا version در خلاصه نیست. categoryCount فقط شمارنده است. ردیف چک ماه/فاصله، markup/down basis point و واحد گردکردن را دارد؛ هیچ مبلغی در خلاصه وارد number جاوااسکریپت نمی‌شود.

## جزئیات، نسخه و فرمان

Payments و Credit reader/DbContext خود را دارند؛ root فقط قراردادها و شمارنده‌ها را ترکیب می‌کند. جزئیات schemaVersion=1 و method/plan نوع‌دار دارند؛ min/max ریال رشته یا null صریح، categoryIds کاملِ همان مورد و version پایه۶۴ rowversion است. شناسهٔ پاسخ در کلاینت به شناسهٔ درخواستی مقید است. بیش از۵۰۰ دسته (حد فعلی ورودی عمومی فرمان) با query حداکثر۵۰۱ و purchase_detail_capacity_unavailable/503 رد می‌شود؛ آرایه ناقص یا حذف بی‌صدای انتخاب برنمی‌گردد. سایر خواندن‌های legacy هنوز حد متفاوت خود را دارند.

در بررسی، نقص واقعی نسخه پیدا شد: تغییر صرفاً ارتباط دسته‌ها می‌توانست parent را Modified نکند، پس rowversion روش/طرح عوض نمی‌شد. هر ویرایش سرویس تازه، parent.NameFa را صریحاً modified می‌کند تا حتی دسته‌تنها/no-op نیز نسخه بچرخد. compare ورودی و WHERE rowversion EF، همراه transaction/audit موجود فرمان، جلوی بازنویسی قدیمی را می‌گیرند. schema عوض نشده است. صحت مثبت SQL/همزمانی این اصلاح هنوز اثبات نشده؛ آزمون‌های واقعی نوشته و فقط compile شده‌اند.

reader ابتدا parent، سپس categoryIds حداکثر۵۰۱ و دوباره version parent را می‌خواند. تغییر بین خواندن‌ها به version_conflict/409 می‌انجامد تا header قدیمی با قواعد جدید به فرم نرسد. این تضمین به عبور writer از سرویس‌های نسخه‌دار تازه وابسته است؛ جای snapshot عمومی صفحه‌ها یا حفاظت در برابر SQL دستی نیست. مسیر POST/PUT، finance.write، کنترل دسته‌ها و audit اتمیک قبلی حفظ شده‌اند. ساخت روش/طرح فرمان idempotency دائمی ندارد؛ رابط پس از نتیجهٔ نامعلوم خودکار دوباره ارسال نمی‌کند.

summary شامل methods/enabledMethods/plans/enabledPlans به‌صورت رشتهٔ decimal صحیح است. شمارنده‌ها مستقل‌اند؛ snapshot مشترک بین countها/ماژول‌ها تضمین نشده. قرارداد JS حالت enabled>total را رد می‌کند و داشبورد خطا/— نشان می‌دهد، نه صفر یا عدد صفحهٔ اول.

## رابط و مالی

صفحهٔ lazy جدید `finance.tsx` دو بخش روش و طرح دارد؛ state فیلتر، seek قبلی/بعدی، خطا/retry/خالی، دریافت جزئیات تازه و read-only مستقل است. هنگام fetch خطادار یا جزئیات ناسازگار، فرم قدیمی برای ذخیره نشان داده نمی‌شود. دریافت جزئیات تازه فرم را حتی با version یکسان بازنشانی می‌کند. دسته‌های انتخاب‌شدهٔ غایب در metadata با شناسه دیده و حفظ می‌شوند؛ حذف فقط صریح است. در نبود metadata ذخیره قفل و دکمهٔ دریافت دسته‌ها خارج از fieldset غیرفعال قابل استفاده است. نقش FinanceManager استاندارد catalog.read دارد؛ این UI جای مجوز سرور نیست.

فرم تازهٔ چک مدت و نرخ خالی دارد و مدیر باید آن‌ها را وارد کند؛ ماه۶ یا نرخ۰ به‌عنوان سیاست تجاری فرض نمی‌شود. واحد پیش‌فرض۱۰ ریال فقط سازگاری A09 است و قابل انتخاب۱/۱۰ باقی است. رقم فارسی/عربیِ مدت/نرخ و مبلغ پذیرفته و نرمال می‌شود. مبلغ‌ها رشتهٔ صحیح ریال با BigInt تا سقف long هستند؛ basis point/تعدادها integer محدودند. modulus ماه/فاصله، سقف نرخ، min≤max و دستهٔ تکراری پیش از ارسال بررسی می‌شوند؛ سرور مرجع نهایی می‌ماند.

پس از0/5xx یا خطای نامعلوم، فرم قفل و توضیح نتیجهٔ نامعلوم می‌آید؛ retry خودکار یا submit دوم از همان فرم وجود ندارد. برای بررسی، فرم بسته و فهرست تازه دریافت می‌شود؛ ویرایش موجود می‌تواند با دریافت صریح جزئیات تازه باز شود.۴۰۴/۴۰۹ نیز ذخیرهٔ draft قدیمی را می‌بندد. ساخت تازه تضمین exactly-once سمت سرور ندارد و QA مثبت قطع پاسخ باقی است. فعال‌کردن طرح/روش درگاه، مدارک یا وصول چک را فعال نمی‌کند. تمام providerها طبق D16 غیرفعال و سیاست واقعی هزینه/گارانتی/چک نامشخص باقی است.

## شواهد و محدودیت پذیرش

- **۳۷۲ بک‌اند موفق**:۱۹ تازه +۳۵۳ رگرسیون؛ فیلتر/cursor/scope، SQL translation محدود، سیاست کامل دسترسی، رد query تکراری و قرارداد native HTTP با reader مصنوعی. SQL یا JWT واقعی در این suite اجرا نشده‌اند.
- **۳۱ contract پنل موفق**: پنج تازه، شامل schema/filter/detail، حفظ دستهٔ غایب، bigint، فرم با ارقام فارسی و رد شروط ناقص. TypeScript و build Vite مستقل `tmp/finance-admin-dist` موفق؛ dist زنده دست‌نخورده است. entry۳۳۱٫۲۳ + schemas preload۸۵٫۶۳، جمع اولیه۴۱۶٫۸۶/gzip۱۲۹٫۴۷kB و finance lazy۱۶٫۳۴/gzip۴٫۸۵kB است؛ هشدار۵۰۰kB ندارد و شاهد CWV/عملکرد دستگاه نیست.
- **پنج wire**: پاسخ واقعی ASP.NET test host با reader مصنوعی در schema تولید TypeScript؛ null صریح، سقف long و شمارندهٔ بالای۲^۵۳ حفظ شدند. `scripts/verification/verify-finance-wire.mts` و `artifacts/checks/finance-wire/report.json`.
- **۳۰ UI محدود** با کامپوننت‌های تولید و transport نمونه؛ تمام سه ذخیره رد شد. روش۵۰/۵۰/۱، صفحهٔ دوم طرح، جست‌وجوی مورد خارج صفحهٔ اول، خالی/فیلتر، جزئیات/دستهٔ غایب/مبلغ دقیق، reset با نسخهٔ یکسان، unknown/conflict، قرارداد خراب و خطای سرویس/retry، بدون metadata، read-only و موبایل۳۹۰×۸۴۴ بررسی شدند.۰ خواندن legacy کامل و۰ Cookie/Authorization در fixture بود. این شاهد نقش/MFA یا ذخیرهٔ واقعی نیست.
- fixture ابتدا در حالت پاسخ ناسازگار، dictionary مشترک خودش را تغییر می‌داد و recovery هم پاسخ ناسازگار می‌گرفت؛ کپی مستقل ردیف اصلاح و فقط fixture اثبات‌شدهٔ خود پروژه restart شد. UI تولید پاسخ خراب را درست رد می‌کرد. دو lifecycle،۳۲ درخواست و console قبل/تب fresh نهایی صفر بودند. مقدار نام/توضیح/مبلغ/کلید log نشد؛ فقط ساختار و categoryIdهای ثابت نمونه ثبت شد.
- **پنج SQL فقط compile/discovery**:۱۰۱ روش و فارسی/category/legacy،۱۰۱ طرح و summary، تغییر فقط دسته/نسخهٔ stale و دو writer همزمان در هر دو ماژول، تغییر میان header/rules با interceptor، نقش مالی/MFA واقعی در برابر نقش محتوا. **کل۹۶؛۵۹ شاهد اجرای قبلی و۳۷ تازه اجرا نشده‌اند.** هیچ‌کدام از پنج مورد این برش اجرا نشده است.
- model checks Payments و Credit بدون تغییر جامانده؛ سورس همچنان۲۰ و main۱۷ است. بازخوانی نسخه و تطبیق زمان/graph با SQL Server واقعی، deadlock/بار/plan و پذیرش فرم متصل هنوز باقی‌اند.

گزارش جمع `artifacts/checks/finance-paging-source.json`، logهای finance-paging-* و finance-layout-ui/http و سه تصویر sayman-finance-* هستند. دو parent/child QA terminal، پورت۳۱۷۵/۵۱۸۱ بسته، تب۲۷/۲۸ بسته، viewport reset و کنترل/پوشهٔ موقت خودشان حذف شدند. Main، Docker، SQL، MFA مالک و Redis چت دست‌نخورده‌اند.

صفحه‌بندی عمومی روش/طرح و انتخاب‌گر assignment کالا، metadata دسته/برند/ویژگی، CMS و بار/طرح query در ادامه باقی‌اند؛ این برش کل مدیریت یا پروژه را کامل نمی‌کند. پس از اعلام پایان آزادسازی، SQL۱۰۳ جاری (هفت مورد Catalog در برش بعدی افزوده شد) و QA ایزولهٔ نقش/MFA/ویرایش/قطع پاسخ انجام و سپس۱۸/۱۹/۲۰ و runtimeهای جدید پذیرفته/منتشر شوند؛ کل دامنهٔ PDF حفظ است.
