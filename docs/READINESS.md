# بررسی آمادگی و سازگاری شِما

این اصلاح عملیاتی پس از بستهٔ یکپارچهٔ ارسال/گوشی آماده شده است. ۲۵ آزمون جدید روی SQL واقعی پس از بازیابی D43 پاس شدند؛ همهٔ fixtureها کوتاه‌عمر و جدا از Sayman اصلی‌اند. شواهد در `readiness-schema-real-sql.log` و TRX هم‌نام ثبت است. پذیرش ۸۵۶ آزمون قبلی مربوط به بستهٔ ثابت قبلی است؛ جمع این دو اجرا نباید به‌عنوان یک اجرای کامل تازهٔ ۸۸۱تایی معرفی شود. وضعیت فعال‌شدن روی اصلی باید از descriptor و hash اجرای جاری بررسی شود.

`GET /health/live` فقط زنده‌بودن فرایند را بررسی می‌کند و به SQL وابسته نیست. `GET /health/ready` باید اتصال SQL، تطبیق کامل تاریخچهٔ مهاجرت هر ۱۲ ماژول با مهاجرت‌های همان executable و آماده‌بودن داده‌های جست‌وجو را بررسی کند. تاریخچهٔ ناقص یا دارای مهاجرت ناشناخته، پاسخ 503 می‌گیرد. خطاهای ارتباط دیتابیس نیز 503 هستند. پاسخ‌ها `no-store` و `noindex, nofollow` دارند و نام دیتابیس، migration یا اطلاعات اتصال را نمایش نمی‌دهند.

بررسی قبلی فقط مهاجرت‌های معوق را می‌دید؛ بنابراین یک executable قدیمی می‌توانست دیتابیس جدیدتر را آماده اعلام کند. بررسی جدید مجموعهٔ مرتب شناسه‌ها را در هر ماژول دقیق تطبیق می‌دهد. هیچ migration، بازگردانی، تغییر تاریخچه یا اصلاح خودکاری انجام نمی‌شود.

## پذیرش لازم

آزمون‌های واقعی `ReadinessSchemaSqlTests` برای هر ۱۲ ماژول، یک marker آینده و یک marker حذف‌شده را در GUID آزمایشی خود بررسی می‌کنند. markerها با نسخهٔ دقیق اولیه در `finally` برگردانده می‌شوند؛ تاریخچهٔ اصلی و دادهٔ تجاری تغییر نمی‌کنند. یک آزمون دیگر قطع اتصال SQL را از زنده‌بودن فرایند تفکیک می‌کند. جمع این کلاس ۲۵ مورد است.

پس از بازیابی SQL و پایان فرایندهای آزمون قبلی، از ریشهٔ پروژه اجرا شود:

```sh
python3 scripts/test-sql-local.py --filter 'FullyQualifiedName~Shop.SqlTests.ReadinessSchemaSqlTests.' --logger 'trx;LogFileName=readiness-schema.trx'
```

این دستور عمداً build دارد؛ `--no-build` روی خروجی‌های قدیمی، اصلاح جدید را آزمایش نمی‌کند. قبولی باید با ۲۵ آزمون اجراشده و صفر خطا در TRX تأیید شود. build ایزوله و کشف آزمون‌ها به‌تنهایی پذیرش SQL نیستند.

## حدود عملیاتی

این health check ابزار تشخیص است و تمام ستون‌ها، indexها یا تغییرات دستی شِما را با مدل مقایسه نمی‌کند. نسخه‌های frozen قدیمی این اصلاح را ندارند؛ بازگشت به آن‌ها پس از ثبت دادهٔ چندبسته‌ای، مجوز یا سازگاری خودکار ندارد. انتشار و بازیابی باید از بستهٔ تأییدشده و فرایند backup/restore مربوط به همان نسخه استفاده کند. دریافت 503 نباید با حذف markerهای واقعی مهاجرت برطرف شود.

اصلاح با مجوز D44 روی API اصلی5080 فعال شد؛ هیچ migration یاseed نداشت.۱۲ بررسی HTTP شامل سلامت باheaderهای دقیق،401سه‌مسیر خصوصی،FA/ENmarket/account/moments وادمین3173 پاس شدند.14DLLبا بستهٔ آزموده دقیق،فایل محیط وکلیدهای قبلی محفوظ وdescriptorهای فروشگاه/ادمین بدونتغییرند. `artifacts/checks/readiness-main-release.json` مرجع است. اعتبار روی Linux/Docker واقعی و تمرین بازیابی این اصلاح هنوز انجام نشده است؛ Docker/Redis در این انتشار restart نشدند.
