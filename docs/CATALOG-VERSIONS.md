پذیرش جدید 2026-10-23: D20 توقف فضا را رفع کرد؛ **۱۲۹/۱۲۹ SQL واقعی** شامل آزمون‌های این برش موفق شدند. اعداد compile-only و توقف D19 متن زیر تاریخی‌اند؛ QA مرورگر متصل، main migration۱۸–۲۱ و Linux x64/بار هنوز جدا باقی‌اند. وضعیت جاری در [STATUS](STATUS.md) است.

وضعیت 2026-10-23: تغییر سورس و آزمون مستقل انجام شده؛ **پذیرش SQL/همزمانی هنوز انجام نشده است**. D19 منتظر اعلام پایان آزادسازی فضاست. Source۲۰/main۱۷ و migrationهای معوق۱۸/۱۹/۲۰ حفظ‌اند؛ این برش schema تازه، SQL/Docker یا restart اجرای اصلی ندارد.

## یافتهٔ بررسی

کاتالوگ پیش از این در ذخیرهٔ برند/دسته/تعریف ویژگی/محصول/تنوع UpdatedAt می‌نوشت؛ بنابراین یافتهٔ Finance به معنی وجود همان نقص معمول در Catalog نبود. با این حال، تبدیل فرمان ویرایش به UPDATE رکورد اصلی به متفاوت‌شدن زمان وابسته بود. اگر ساعت یک لحظهٔ تکراری برگرداند، تغییر صرفاً فرزند می‌توانست بدون UPDATE رکورد نسخه‌دار والد انجام شود. هدف تازه این است که هر فرمان ویرایش، مستقل از دقت/تغییر ساعت، والد و تنوع‌های صریح ورودی را نسخه‌دار کند.

خواندن مدیریت کالا و دسته/ویژگی از AsSplitQuery استفاده می‌کرد: header و rowversion در یک SELECT و ارتباط‌ها در SELECTهای بعدی می‌آمدند. در فاصلهٔ این queryها امکان ترکیب header قبلی و ارتباط‌های تازه وجود داشت؛ وجود version در DTO به‌تنهایی جلوی آن را نمی‌گرفت.

## تغییر نوشتن

CatalogService زمان فرمان را از TimeProvider موجود برنامه می‌گیرد؛ در اجرای معمول همان System است. Touch برای رکورد تازه CreatedAt/UpdatedAt را یکسان می‌گذارد و برای رکورد موجود UpdatedAt را صریحاً modified می‌کند، حتی اگر مقدار زمان همان قبلی باشد. SQL rowversion همچنان مرجع concurrency است و timestamp جای آن نمی‌نشیند. هیچ شمارنده/توکن مصنوعی جای SQL rowversion ساخته نشده است.

والد Brand/Category/AttributeDefinition/Product و هر تنوع موجودِ صریح ورودی این رفتار را دارند. تنوع فعالِ حذف‌شده از ورودی، soft-disable و stamp می‌شود؛ تنوعی که از قبل غیرفعال بوده و در ورودی نیست دست‌نخورده می‌ماند. تصویر تازه/تغییر ترتیب یا asset binding هم زمان مناسب می‌گیرد و تاریخچهٔ قیمت تازه از همان clock استفاده می‌کند. تاریخچه فقط هنگام تغییر قیمت فروش ثبت می‌شود؛ تغییر رابطه یا no-op نباید قیمت تاریخی ساختگی بسازد. CreatedAt دادهٔ موجود بازنویسی نمی‌شود.

چک version محصول و تنوع، validation تایپ ویژگی‌ها/گزینه‌ها/دسته و روابط مجاز خرید حفظ‌اند. transaction Serializable/audit گروه مدیریت و قیود FK قبلی نیز حفظ شده‌اند؛ کنترل هفت SQL تازه باید نشان دهد rollback شکست audit، نسخه/رابطه/قیمت/history را با هم برمی‌گرداند. اثر واقعی rowversion روی SQL Server از تست واحد قابل استنتاج نیست و هنوز پذیرفته نشده است.

## تغییر خواندن

CatalogReadVersions پس از materialize شدن graph، Id/Version همان رکوردها را دوباره می‌خواند. فقط این دو ستون، بدون قیمت، توضیح یا graph ارتباط، در queryهای حداکثر۵۰۰ شناسه خوانده می‌شوند.۵۰۰ اندازهٔ batch فنی است؛ سقف تعداد محصول/تنوع یا truncation داده نیست. نسخه‌های اصلی کپی می‌شوند تا buffer تغییرپذیر Entity نتیجهٔ بررسی را عوض نکند. duplicate حتی در دو batch متفاوت، version غیر۸بایتی، رکورد حذف‌شده یا version متفاوت، نتیجه را رد می‌کند. graph خالی query اضافه ندارد.

- `IAdminProducts.DetailAsync`: محصولِ تک‌درخواست و تمام تنوع‌های خوانده‌شده، قبل از ساخت DTO دوباره بررسی می‌شوند.
- `CatalogService.AdminMetadataAsync` و `AdminReadAsync` legacy: دسته‌ها و تعریف‌های ویژگی بعد از ترجمه/قواعد/گزینه‌ها بررسی می‌شوند؛ در حالت کامل، محصول‌ها و تنوع‌های همان graph هم بررسی می‌شوند.
- برندِ تک‌جدولی graph فرزند ندارد؛ نسخهٔ فرمان‌های نوشتن آن مستقل از ساعت شد ولی خواندن تک‌جدولی جدیدی به آن اضافه نشده است.

تعارض با همان version_conflict/409 و پیام عمومی بدون مقدار داده برمی‌گردد؛ پاسخی از graph ناسازگار یا آرایهٔ ناقص ارسال نمی‌شود. endpoint، DTO، مجوز catalog.read/write و no-store تغییر قرارداد ندارند. UI موجودِ خطای دریافت جزئیات، دکمهٔ دریافت دوباره دارد؛ این برش سورس/رندر رابط را تغییر نداد و QA متصل آن را دوباره انجام نداد.

این بررسی optimistic است و snapshot سراسری کاتالوگ یا lock خواندن نمی‌سازد. ویرایش پس از پایان بررسی می‌تواند پاسخ را کهنه کند؛ نسخهٔ همان پاسخ هنگام Save دوباره بررسی می‌شود. تضمین graph به رعایت چرخش نسخه در writerهای مجاز بستگی دارد؛ SQL دستیِ تغییر فرزند بدون چرخاندن هیچ والد/تنوعی پوشش ندارد. مسیرهای عمومی کاتالوگ، Cart/Checkout و maintenance مشتق‌های جست‌وجو در این برش تغییر نکردند؛ بررسی آن‌ها کار مستقل بعدی است. metadata و graph تک‌محصول همچنان محدودسازی/plan/بار خود را لازم دارند؛ batch نسخه جای pagination نیست.
