## یافته و مرز تغییر

ReadCartVariantsAsync از قبل قیمت و اطلاعات نمایشی را در یک projection SQL می‌خواند و تغییر نکرد. ReadCheckoutVariantsAsync قبلاً ابتدا همین قرارداد سبد و سپس SKU/version/گارانتی و روابط خرید را می‌خواند. مسیر رسمی quote/order از قبل با SalesTransactionCoordinator، transaction مشترک Serializable در Sales/Catalog/Inventory/Payments/Credit دارد؛ این حفاظت حفظ شده است و نقص مالیِ اثبات‌شده‌ای در آن مسیر ادعا نمی‌شود. reader خارج این transaction و graph عمومی split نیاز به کنترل مستقل داشتند.

CheckoutCatalogQuery اکنون قیمت، نام/label، SKU، گارانتی، SellerId و نسخه‌های محصول/تنوع/دسته/برندِ واجد انتشار را در یک projection می‌گیرد. روابط روش محصول/تنوع و طرح جدا خوانده می‌شوند؛ سپس نسخه‌های همان رکوردها دوباره بررسی می‌شوند. قیمت صحیح long ریال و PriceVersion همان تنوع از یک ردیف‌اند. روش‌های خالی تنوع همچنان ارث‌بری null دارند؛ دادهٔ واجد شرایطِ غایب همچنان غایب است، نه خطای تبدیل‌شده به قیمت/موجودی صفر.

ReadCore عمومی بعد از خواندن ترجمه‌ها، قواعد، مقادیر، گزینه‌های مورد استفاده، رسانه و روابط، دسته/تعریف/برند/محصول/تنوع را تأیید می‌کند. تعریف غایب هنگام ساخت DTO به تعارض خواندن می‌انجامد. بررسی فقط Id/Version، batch۵۰۰ و clone buffer است؛ snapshot خراب یا duplicate سراسری قبل از I/O رد می‌شود.

Search انتخاب winner را با نسخهٔ محصول/تنوع/برند در یک query انجام می‌دهد. hydration باید همان نسخه‌ها و شناسهٔ تنوع قابل نمایش را برگرداند؛ نسخهٔ دسته‌های مبنای scope و تعریف‌های فیلتر نیز کنترل می‌شوند. Lookup انتخاب اولیهٔ محصول منتشرشده را با نسخه به hydration وصل می‌کند و دوباره انطباق ID/slug/تنوع فعال را بررسی می‌کند؛ انتخاب قدیمی slug یا تنوع غیرفعال به کالای نامرتبط تبدیل نمی‌شود. بودجهٔ تلاش در search/lookup بیرونی است و retry تو در تو ندارد.

CatalogReadRetry فقط version_conflict این خواندن‌های بدون mutation را حداکثر دو بار از ابتدا اجرا می‌کند. ناپایداری در هر دو تلاش، catalog_unavailable/503 می‌دهد؛ cancellation، validation، maintenance و خطای SQL به retry تبدیل نمی‌شوند. تراکنش شکست‌خورده/SQL deadlock دوباره استفاده نمی‌شود؛ هماهنگ‌کنندهٔ رسمی قبلی همچنان مسئول commit/rollback است. مدیریت همچنان version_conflict/409 می‌گیرد و retry خودکار فرمان ندارد.

DTO/endpoint/مجوزها و no-store تغییر شکل ندارند؛ پول JSON همچنان رشتهٔ دهدهی ریال است. BFF/SSR موجود در حالت API پاسخ ناموفق را unavailable می‌کند؛ fallback نمونه اضافه نشده و سورس Next/Vite این برش تغییر نکرد. هیچ provider موفقیت ساختگی ندارد.

## محدودیت تضمین

این کنترل optimistic است، snapshot سراسری کاتالوگ نیست. تغییر پس از تأیید می‌تواند پاسخ را کهنه کند. writer مجاز باید نسخهٔ والد/تنوع مربوط را بچرخاند؛ SQL دستیِ تغییر فرزند بدون هیچ bump پوشش ندارد. شمارش، مرزبندی/ترتیب صفحه و موجودی میان queryهای مختلف snapshot مشترک ندارند؛ insertion phantom یا تغییر availability را رزرو/تضمین قیمت تلقی نکنید. موجودی نهایی و ثبت سفارش همچنان قواعد/قفل/رزرو خودشان را لازم دارند. pagination متادیتا، graph بسیار بزرگ، query plan/بار و هزینهٔ queryهای تأیید باقی است.

Filters/FacetValues و maintenance فیلدهای مشتق جست‌وجو در این برش تغییر نکردند؛ audit مستقل آن‌ها گام بعدی است. نمایش بدون تغییر UI به معنی پذیرش کاربر/SQL متصل نیست.
