## قرارداد و مالکیت

Sales مالک `AddressBooks` و `Addresses` است. `GET /api/addresses` فقط دفتر حسابِ `sub` نشست access را برمی‌گرداند: schemaVersion=1، capacity=20 و حداکثر۲۰ نشانی. مهمان، mfa_pending و mfa_recovery حق دسترسی ندارند. هیچ owner از query یا body پذیرفته نمی‌شود؛ query در کل این گروه ممنوع است. همهٔ پاسخ‌ها no-store و limiter مستقل۶۰ درخواست/دقیقه/کاربر دارند. Origin ارسالی باید دقیقاً مجاز باشد؛ برای تغییر، وجود Origin الزامی است.

`PUT /api/addresses/{id}` از UUID غیرصفر مشتری (قالب canonical در BFF:۳۲ hex کوچک) برای ساخت قابل تکرار استفاده می‌کند. ورودی: label، contactName، contactPhone، delivery={countryCode:IR,province,city,address,postalCode}، makeDefault صریح و version=null برای ساخت/نسخهٔ فعلی برای ویرایش. نرمال‌سازی Unicode قبل از trim انجام می‌شود تا نتیجه با تکرار تغییر نکند؛ یک رگرسیون مستقل این حالت را پوشش می‌دهد. عنوان۱–۶۰، نام۲–۱۰۰، استان/شهر۲–۱۰۰، نشانی۱۰–۲۰۰۰ و کدپستی۱۰رقم است. رقم فارسی/عربی و +98/0098 طبق همان قواعد فرم سفارش نرمال می‌شوند؛ نام/عنوان کنترل‌کاراکتر ندارند و نشانی چندخطی مجاز است. فیلد اضافه در root ورودی رد می‌شود؛ BFF کل ساختار تودرتو را strict می‌خواند.

ساخت تازه۲۰۱ و ویرایش/تکرار ساخت۲۰۰ می‌دهد. تکرار ساخت فقط برای همان حساب، همان resource موجود و fingerprint/اطلاعات فعلی یکسان پذیرفته می‌شود؛ همان ردیف و نسخهٔ جاری برمی‌گردد و اثر «پیش‌فرض‌شدن» دوباره اجرا نمی‌شود. تغییر payload یا تکرار ساخت پس از ویرایش اطلاعات، تعارض است. این تضمین تا وجود resource است؛ دفتر نشانی tombstone دائمی یا تاریخچهٔ فرمان ندارد و بعد از حذف، همان UUID از نظر PUT قابل ساخت دوباره است. برای نتیجهٔ نامعلوم، دریافت فهرست تازه راه بررسی وضعیت فعلی است.

`DELETE /api/addresses/{id}` body نسخهٔ فعلی را می‌خواهد و۲۰۴ می‌دهد؛ ردیف حساب دیگر مانند ردیف مفقود۴۰۴ است. ویرایش/حذف با نسخهٔ قدیمی۴۰۹؛ ظرفیت پر۴۰۰/address_limit؛ خرابی رمز یا قرارداد دفتر۵۰۳/address_unavailable است و هرگز به دفتر خالی/دادهٔ نمونه تبدیل نمی‌شود. خطای JSON/نوع محتوا در middleware پاسخ۴۰۰/۴۱۳/۴۱۵ مناسب دارد و جزئیات خطا افشا نمی‌شود؛ این اصلاح با آزمون native ورودی دارای فیلد اضافه بررسی شد.

## تراکنش و دادهٔ خصوصی

هر تغییر transaction Serializable و قفل UPDLOCK/HOLDLOCK روی marker حساب دارد؛ ساخت اولین marker هم زیر همان قفل بازه‌ای است. rowversion، سقف۲۰ و جابه‌جایی پیش‌فرض با همان تراکنش هماهنگ می‌شوند. unique filtered index حداکثر یک پیش‌فرض را تضمین می‌کند؛ مسیرهای سرویس برای دفتر غیرخالی دقیقاً یکی نگه می‌دارند. اولین نشانی پیش‌فرض است؛ makeDefault=false پیش‌فرض فعلی را حذف نمی‌کند. حذف پیش‌فرض، قدیمی‌ترین نشانی باقی‌مانده برحسب CreatedAt/Id را انتخاب می‌کند. تغییر پیش‌فرض نسخهٔ ردیف قبلی را هم منسوخ می‌کند. هیچ FK به Identity یا DbContext ماژول دیگر وجود ندارد.

label/نام/همراه/تحویل و fingerprint ساخت در payload حفاظت‌شدهٔ Data Protection ذخیره می‌شوند؛ ستون plaintext برای آن‌ها وجود ندارد. root، قرارداد `IAddressProtection` را با purpose مستقل `Sayman.Sales.AddressBook.v1` و binding حساب+شناسه پیاده می‌کند؛ Sales وابستگی ASP.NET ندارد. ciphertext خصوصی حداکثر۳۲۷۶۸ نویسه است. انتقال ciphertext بین حساب/نشانی یا خرابی آن قابل رمزگشایی نیست. read حداکثر۲۱ ردیف می‌گیرد تا ظرفیت/پیش‌فرض ناسازگار را صریحاً رد کند. شناسه، پیش‌فرض، زمان‌ها، revision و rowversion متادیتای plaintext هستند.

key ring موجود برنامه برای خواندن آینده لازم است؛ پاک‌کردن کلیدها داده را غیرقابل‌خواندن می‌کند. حفظ کلیدهای بازنشسته، حفاظت key directory و backup/restore مشترک DB+keys باید در پذیرش عملیات آزموده شود؛ آزمون انجام‌شدهٔ این برش فقط provider موقت و binding/خرابی رمز است. شمارهٔ گیرنده هیچ contact verification یا تغییر مشخصات ورود ایجاد نمی‌کند. رمزنگاری این برش مختص دفتر نشانی است؛ snapshot سفارش قرارداد پیشین خودش را دارد و این برش آن را بازنویسی یا رمزنگاری مجدد نمی‌کند.

## فروشگاه و مرز حافظه

صفحهٔ `/fa/addresses` و `/en/addresses` از حساب لینک دارد؛ بازگشت امن ورود فقط مسیر دقیق `/addresses` یا tab=addresses را می‌پذیرد. در preview مدیریت واقعی در دسترس نیست. عضو، صفحهٔ جدا با key حساب/زبان می‌گیرد؛ unmount درخواست را abort و draft/pending را پاک می‌کند. نشست در حافظه است و پاسخ دیررسِ پس از تغییر حساب در CustomerSessionStore رد می‌شود. هیچ نشانی، draft، token یا pending جدیدی وارد localStorage/IndexedDB/query cache/URL نمی‌شود.

رابط ظرفیت، عنوان/گیرنده/تحویل، پیش‌فرض، فرم اعتبارسنجی، تأیید حذف، خطا/تعارض/فهرست تازه و نتیجهٔ نامعلوم دارد. در قطع پاسخ، فرم قفل می‌شود؛ تلاش صریح همان id/body/version را می‌فرستد. دریافت فهرست تازه، فرم و pending را کنار می‌گذارد. address-client خود mutation را خودکار retry نمی‌کند؛ transport نشست همان قاعدهٔ قبلی نوسازی پس از۴۰۱ و retry همان حساب را دارد. ذخیرهٔ فرم و سفارش مجزا هستند.

انتخاب‌گر فقط در سفارش فیزیکی ظاهر می‌شود و انتخاب اولیه خالی است. «کپی در فرم سفارش» فقط گیرنده، همراه، استان، شهر، نشانی و کدپستی را جایگزین می‌کند؛ note/رضایت را تغییر نمی‌دهد. فیلدها سپس قابل ویرایش‌اند. هنگام busy/uncertain یا وجود درخواست سفارش frozen، کپی ممنوع است. سفارش همان snapshot مستقل قبلی را ثبت می‌کند و reference زنده به دفتر ندارد؛ ویرایش/حذف بعدی دفتر سفارش قبلی را عوض نمی‌کند. UI این مرز را توضیح می‌دهد؛ آزمون SQL آن نوشته شده و هنوز اجرا نشده است.

BFF جدا فقط GET root و PUT/DELETE resource معتبر را می‌پذیرد؛ exact Origin، bearer، ورودی۱۶KiB، پاسخ۵۱۲KiB، timeout۱۲ثانیه، redirect:error، schema strict و تطبیق id پاسخ دارد. cookie/اختیار مدیر/جزئیات خطای upstream عبور نمی‌کنند. responseها private,no-store و noindex هستند. PWA هیچ HTML/RSC/API خصوصی را cache نمی‌کند؛ addresses هم به گیت جلوگیری از activation/update در تب حساس افزوده شد. صفحات build واقعی Cache-Control خصوصی/no-store و robots=noindex دارند.

## شواهد و کار باقی

- **۳۵۳ بک‌اند موفق**:۱۸ تازه شامل نرمال‌سازی/اعتبارسنجی، binding/خرابی رمز، مدل/index/SQL translation، مجوز/Origin/owner از claim و پاسخ واقعی test host با سرویس مصنوعی. هیچ SQL یا JWT واقعی در این دسته اجرا نشده است.
- **۱۱۶ فروشگاه موفق**:۹ تازه address/schema/BFF/client/session/returnTo؛ تست موجود PWA برای عدم interception و منع activation در addresses نیز توسعه یافت. مبلغ جدیدی در این قرارداد نیست و قواعد ریال تغییر نکردند.
- **۲ wire**: JSON پاسخ HTTP واقعی ASP.NET test host با IAddressBook مصنوعی، در schema تولید TypeScript خوانده شد. `scripts/verify-address-wire.mts` و `artifacts/checks/address-wire/report.json`.
- **۱۹ UI محدود**: کامپوننت تولید با transport مستقل و دادهٔ نمونه، همهٔ تغییرها رد شدند؛ خالی/فیلد/فارسی/انگلیسی/کپی صریح/freeze/قطع پاسخ/retry/تعارض/قرارداد خراب/موبایل۳۹۰×۸۴۴.۲۰ درخواست، پنج write ردشده، دو تکرارِ دقیقِ درخواست و صفر Cookie/Authorization در fixture. مقدار ورودی log نشد. خروجی debug مخصوص fixture ابتدا overflow داشت و wrap شد؛ دو console error مخصوص remount هنگام HMR نمونه ثبت است و تب fresh نهایی خطا/هشدار صفر داشت. جای گردش متصل نیست.
- **۱۲ HTTP build واقعی Next**: ده مرز BFF و دو صفحهٔ FA/EN؛ fixture فقط metadata عمومی می‌دهد و همهٔ auth/عملیات شکست می‌خورند. `address-next-http.json`؛ بدون ورود موفق/سفارش/SQL.
- Next build نهایی ایزوله و TypeScript موفق؛ `.next` و runtime اصلی دست‌نخورده‌اند. Sales model بدون تغییر جامانده و SQL idempotent تازه تولید شد؛ migration۲۰ `CustomerAddressBook` فقط سورس است. build SQL صفر warning/error؛ discovery فقط۹۱ مورد را نشان داد.
- **هفت SQL تازه فقط کامپایل شده**: CRUD/رمز/پیش‌فرض، مالکیت، replay/نسخه، ظرفیت/نسخهٔ پیش‌فرض، ایجاد و default همزمان، rollback شکست رمز و استقلال snapshot سفارش. کل۹۱؛۵۹ شاهد اجرای پیشین و۳۲ تازه اجرا نشده‌اند. قفل/unique/default/race/replay/rollback به SQL Server واقعی نیاز دارند.

گزارش جمع `artifacts/checks/address-book-source.json`، logهای address-book-*، address-layout-ui/http و تصاویر sayman-addresses-* هستند. QA parent/child terminal، پورت‌های۳۱۰۵/۳۱۷۵/۵۱۸۱ بسته، تب۲۵/۲۶ بسته و viewport reset شد؛ کنترل/پوشهٔ موقت خود QA حذف شد. SQL/Docker/main/Redis چت تغییر نکردند.
