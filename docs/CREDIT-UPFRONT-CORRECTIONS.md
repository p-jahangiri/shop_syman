# اصلاح گواهی پیش‌پرداخت پس تعهد — A95/A96، source79 پذیرفته و منتشرنشده

ادامهٔ D34 و قاعدهٔ D35 است؛ انتقال یا استرداد واقعی وجه نیست. سفارش چکی CreditApproved پیش dispatch می‌تواند با تأیید صریح FinanceMFA، دلیل خصوصی و همان مبلغ اصل سفارش، گواهی دریافت را باطل و سپس دوباره تأیید کند. صفر واقعی همان ConfirmNoUpfrontDue است. هیچ مبلغ، موجودی، قیمت، تاریخ رزرو، scope یا حالت نقدی Paid از این مسیر تغییر نمی‌کند. پس dispatch یا تحویل، این برش اصلاح را مسدود می‌کند؛ حسابداری استرداد واقعی مستقل و وابسته به درگاه/رویهٔ واقعی است.

همان دفتر append-only UpfrontEvents/Commands و گیت مشترک owner در Sales استفاده می‌شود. قرارداد داخلی Sales فقط مرحلهٔ ارسال و نسخهٔ سفارش را می‌خواند؛ Credit به DbContext ماژول دیگر دسترسی ندارد. root Identity/Sales/Credit Serializable فعلی کافی است؛ موجودی نوشته نمی‌شود. dispatch و اصلاح بر همان ownergate سریال می‌شوند. آگاهی صریح `AcknowledgedCommittedOrder=true` و Note غیرخالی برای هر فرمان روی CreditApproved ضروری است؛ دستور legacy بدون این پرچم پس تعهد همچنان رد می‌شود. این پرچم روی سفارش معمولی پذیرفته نمی‌شود. هیچ head تازه‌ای پس تعهد ساخته نمی‌شود؛ تأیید مجدد فقط پس Revoked و همان head/مبلغ محفوظ است.

پرچم در sealed event و رسید خصوصی می‌ماند؛ برای legacy مقدارfalse از JSON حذف می‌شود تا payload hash و event JSON قبلی دقیق بماند. پارامتر اختیاریfalse در خواندن اسناد قدیمی مجاز است؛ افزودن پرچمtrue به receipt یا event محافظت‌شده بدون مهر معتبر ناممکن است. Customer همان summary قبلی و بدون مرجع/دلیل/پرچم خصوصی را می‌بیند. receipt همان UUID پیش CAS و وضعیت جاری replay می‌شود.

OccurredAt اصلاح تعهدی می‌تواند تاریخ واقعی قدیمی‌تر از رویداد قبلی باشد، ولی داخل بازهٔ CreatedAt تا now و UTC است؛ RecordedAt و sequence همچنان صعودی‌اند. این اجازه فقط روی رویداد sealed با پرچم صریح تعهدی اعمال می‌شود؛ قواعد تاریخ legacy تغییر نمی‌کنند. تغییر نسخهٔ upfront، evidence گواهی clearance قبلی را stale می‌کند. حتی تأیید مجدد دریافت، به‌تنهایی ارسال را آزاد نمی‌کند؛ Finance باید clearance تازه را بازبینی کند. موجودی Allocated و مهلت اصلی محفوظ‌اند.

پنل عملیات خالی، acknowledgment پیش‌فرضfalse، preview مبلغ و اثر اصلاح، دلیل خصوصی، تاریخچه، journal RAM/GET رسید/خروج چندتب دارد. تأیید و بازخوانی قابلیت‌ها سروری است. پس dispatch گزینه‌ها مسدود و دلیل روشن است. source79 code-only و بدون migration تازه طراحی شده؛ source78 پذیرفته و اصلی73 تغییر نمی‌کنند. پذیرش SQL واقعی شامل race با dispatch، audit rollback، legacy hash/replay، stale clearance، reapprove/warehouse و مرز پس ارسال، decoder واقعی، UI/mobile/قطع پاسخ/cleanup لازم است. پذیرش A96 انجام شد؛ artifact source-acceptance و STATUS مرجع دقیق آزمون‌ها، خطای fixture و جایگزینی کل کلاس، cleanup و runtime نهایی‌اند. اصلی73 تغییر نکرده است.
