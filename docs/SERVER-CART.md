# سبد سروری: API و مرز فروشگاه

سبد Sales، API، مسیر واسط Next و رابط فروشگاه اکنون در حالت API متصل‌اند. AuthProvider نشست را در کل فروشگاه نگه می‌دارد و ShopProvider اقلام، قیمت و موجودی سبد را از سرور می‌خواند. حالت preview با provider مستقل، همچنان صریح و جداست. هیچ سفارش، رزرو یا پرداختی از تغییر سبد ساخته نمی‌شود.

## مالکیت و نگهداری

Sales مالک schema هفتم `sales` و جدول‌های `Carts` و `CartLines` است. migration پانزدهم `ServerCarts` و SQL idempotent در `backend/sql/sales.sql` قرار دارند. سبد فقط شناسهٔ تنوع و تعداد را نگه می‌دارد؛ قیمت یا هویت ارسالی مرورگر مرجع نیست. FK میان ماژول‌ها وجود ندارد. Catalog از `ICartCatalogReader` و Inventory از `IInventoryReader` مصرف می‌شوند؛ Sales context آن‌ها را نمی‌خواند.

مشتری با sub توکن معتبر access شناخته می‌شود. API هیچ OwnerId یا CartId قابل انتخابی ندارد. توکن ناقص MFA و Authorization نامعتبر به سبد مهمان برنمی‌گردند. مهمان یک توکن تصادفی۲۵۶بیتی در کوکی HttpOnly/SameSite=Strict دارد؛ فقط SHA256 آن در SQL ذخیره می‌شود. کوکی `sayman_cart` با Path=/api/cart در Production به Secure نیاز دارد. عمر ثابت۳۰روز مرز فنی اولیه است؛ سیاست نهایی نگهداری و پاک‌سازی داده هنوز تأیید/پیاده نشده است. سبد حساب تا گردش پاک‌سازی آینده محفوظ می‌ماند.

GET بدون کوکی/حساب سبد مجازی خالی می‌دهد و هیچ ردیف یا کوکی نمی‌سازد. نخستین PUT موفق مهمان، ردیف و کوکی را می‌سازد. رزروِ موجودی به مرحلهٔ ثبت سفارش تعلق دارد؛ سبد فقط موجودی جاری را نشان می‌دهد.

## قرارداد

| مسیر | ورودی/اثر |
|---|---|
| GET `/api/cart/fa` یا `/en` | سبد همان هویت؛ قیمت/موجودی/عنوان جاری از سرور |
| PUT `/api/cart/{locale}` | `{lines:[{variantId,quantity}],version}`؛ جایگزینی مطلق اقلام |
| POST `/api/cart/{locale}/merge` | access معتبر و کوکی مهمان؛ ادغام یک‌باره و حذف کوکی |

حداکثر۶۴ تنوع متمایز و تعداد۱ تا۱٬۰۰۰٬۰۰۰؛ حذف با حذف قلم از آرایه و خالی‌کردن با `lines:[]`. version همان rowversion به Base64 است. تغییر با نسخهٔ قدیمی409 می‌دهد؛ تکرار PUT که اقلامش دقیقاً با وضعیت جاری برابر است، بدون mutation یا تغییر version همان سبد را برمی‌گرداند. این رفتار جای idempotency پایدار سفارش/پرداخت آینده نیست؛ replay قدیمی پس از تغییر متفاوت، مجوز بازنویسی ندارد.

سبد `schemaVersion,locale,version,lines,subtotalRial,hasIssues` دارد. هر قلم تعداد درخواست‌شده، اطلاعات عمومی قابل خرید، `unitPriceRial,lineTotalRial,available,issue` دارد. تمام مبلغ‌ها رشتهٔ صحیح ریال‌اند. هزینهٔ ارسال و مالیات در subtotal نیستند و همچنان تعیین نشده‌اند؛ این خروجی quote تضمین‌شده یا مبلغ قابل پرداخت نیست.

قلم تازه/افزایش تعداد فقط برای تنوع فعال کالای Published در دسته/برند فعال، پس از زمان انتشار و تا موجودی جاری مجاز است. افت موجودی پس از افزودن، مقدار درخواست‌شده را بی‌صدا کم نمی‌کند: `insufficient_stock` نمایش داده می‌شود. غیرفعال‌شدن محصول، قلم `unavailable` بدون عنوان/قیمت منتشرنشده و با امکان حذف می‌دهد. افزایش قیمت فراتر از سقف bigint ریال باعث500 یا گردشدن نمی‌شود: نوشتن تازه رد و خواندن سبد قبلی با `amount_limit` و subtotal تهی گزارش می‌شود. هیچ عدد مالی به JavaScript Number تبدیل نمی‌شود.

## همزمانی و ادغام

فرمان‌های سبد تراکنش ReadCommitted مستقل دارند. application lock مشترک برای خواندن و انحصاری برای ویرایش، به هویت همان سبد محدود است. ادغام، دو کلید عضو/مهمان را با ترتیب ثابت قفل می‌کند؛ قفل سراسری سبدها وجود ندارد. Revision داخلی تضمین می‌کند تغییر تعداد حتی در یک tick ساعت، rowversion را تازه کند. شکست قفل نتیجهٔ منفی را بررسی و rollback می‌کند. کارایی/بار جدا باید آزموده شود.

ادغام تعدادهای یک تنوع را جمع می‌کند و سقف‌ها/مبلغ را بررسی می‌کند. موجودی کمتر از جمع یا ناموجودشدن کالا، اقلام را حذف نمی‌کند؛ نتیجه نیاز به بررسی نشان می‌دهد. مهمان پس از commit خالی و به tombstone مصرف‌شده تبدیل می‌شود. تکرار برای همان عضو، سبد فعلی عضو را می‌دهد؛ حساب دیگر اجازهٔ مصرف مجدد یا خواندن آن مهمان را ندارد. خطای درج/قید SQL همهٔ تغییرات عضو و مهمان را rollback می‌کند. سبد عضو با خروج از حساب حذف نمی‌شود؛ رابط بعدی باید حافظهٔ خصوصی را هنگام خروج پاک کند.

## مسیر Next و امنیت

همان URLهای `/api/cart/...` در Next به API ثابتِ `SHOP_API_URL` وصل‌اند. origin صریح معتبر `SHOP_PUBLIC_URL` و حالت API لازم است. مسیر/روش whitelist، body حداکثر۱۶KiB، پاسخ حداکثر۲۵۶KiB و Zod ورودی/خروجی اعمال می‌شود. واحد مبلغ، جمع و عدم وجود فیلدهای خصوصی نیز کنترل می‌شود. خطا به fixture برنمی‌گردد و پاسخ upstream خام منتشر نمی‌شود.

فقط Authorization و کوکی `sayman_cart` به API می‌روند؛ refresh/admin cookies و headerهای پنل منتقل نمی‌شوند. فقط Set-Cookie همین نام از API برمی‌گردد. Origin نامعتبر رد می‌شود؛ همهٔ پاسخ‌ها `private,no-store` و noindex هستند. Service Worker این API را intercept یا cache نمی‌کند؛ مورد صریح `/api/cart/fa` به تست مرز PWA افزوده شد. هیچ توکن، hash، cart یا پاسخ مالی در گزارش HTTP ذخیره نشده است.

## شواهد

- ۹ سناریوی تازه SQL: CRUD مهمان و پول بزرگ، رقابت نسخه، قیمت/موجودی جاری و قلم غیرفعال، ادغام همزمان/تکراری، ادغام با JWT واقعی مشتری و جداسازی حساب، خطای عمدی SQL و rollback ادغام، overflow مبلغ، قلم/مقدار نامعتبر و انقضای مهمان. مجموع۳۱ تست SQL موفق‌اند.
- ۱۱ تست تازه اعتبارسنجی/Origin/دسترسی به مجموع۱۱۷ تست بک‌اند افزوده شدند. ۴ تست Zod اولیه و۱۳ تست تازهٔ نشست/انتقال/مرز cart به مجموع۶۲ تست فروشگاه رسیده‌اند؛ build تولیدی و TypeScript موفق‌اند.
- migration پانزدهم روی Sayman اعمال شد؛ مدل Sales تغییر جامانده ندارد و readiness هفت context موفق است. API5080 و Next3000 با build تازه فعال‌اند.
- `python3 scripts/smoke-server-cart.py`: چهارده بررسی واقعی BFF→API→SQL، شامل کوکی، دو زبان، replay/version، ورودی/Origin/اندازه، احراز نامعتبر و clear موفق‌اند. مهمان مستقل تست در پایان خالی شد؛ cookie/credential در فایل نوشته نشده است. گزارش `artifacts/checks/server-cart-http.json`.

اتصال UI و نشست، انتقال سبد قبلی و QA مسیرهای اصلی مرورگر انجام شدند. quote معتبر و snapshot سفارش، خرید مهمان/آدرس، ارسال/مالیات، ثبت سفارش/رزرو و پرداخت واقعی هنوز باقی‌اند. SQL محلی با Rosetta جای پذیرش Linux x64 و بار را نمی‌گیرد.

## نشست و رابط متصل

در حالت API، access token فقط در حافظهٔ AuthProvider است؛ ورود/تأیید MFA، refresh و خروج از مسیر مشتری انجام می‌شوند. بازکردن صفحهٔ حساب برای نگه‌داشتن نشست لازم نیست. refresh موازی همان صفحه coalesce و در مرورگرهای دارای Web Locks بین تب‌ها با قفل قبلی `sayman-customer-refresh` هماهنگ می‌شود. پیام BroadcastChannel فقط نوع signin/signout است، بدون شناسه یا توکن. پاسخ دیررس ورود/refresh پس از خروج یا تغییر هویت کنار گذاشته می‌شود. پس از401، درخواست cart فقط با همان عضو مجدداً ارسال می‌شود؛ با هویت دیگر یا مهمان replay نمی‌شود.

401ِ بررسی نشست، مهمان است؛ خطای سرویس به مهمان یا fixture تبدیل نمی‌شود. در خروج ناموفق، حافظهٔ خصوصی پاک و وضعیت «خروج ناتمام» گزارش می‌شود؛ یک flag غیرمحرمانه در sessionStorage باعث می‌شود تلاش بعدی ابتدا خروج را تمام کند. ذخیره‌ساز محدود فقط حافظهٔ همان صفحه را دارد؛ خروج ناموفق کامل اعلام نمی‌شود. مرورگرهای قدیمی فاقد Web Locks هنوز نیاز به پذیرش چندتب جدا دارند.

BFF هویت نیز اکنون Origin صریح، حدود body/response، `private,no-store` و cookie/header whitelist دارد. فقط کوکی `sayman_refresh` و Authorization مشتری به API می‌روند و فقط Set-Cookie همین نام برمی‌گردد؛ headerها و کوکی پنل منتقل نمی‌شوند. setup Authenticator از این مسیر مجاز نیست. credential یا پاسخ auth/cart وارد localStorage و Cache Storage نمی‌شود.

ShopProvider خصوصی، snapshot را به scope هویت محدود می‌کند و با خروج/تغییر حساب، snapshot قبلی را نمایش نمی‌دهد. ویرایش تا پاسخ سرور optimistic اعلام نمی‌شود؛ عملیات همزمان همان صفحه محدود و بین تب‌های دارای Web Locks مرتب می‌شوند. نسخهٔ قدیمی refresh می‌شود و کاربر باید انتخابش را دوباره انجام دهد؛ intent قدیمی خودکار روی وضعیت تازه اعمال نمی‌شود. پاسخ قدیمیِ read پس از write جدید، با generation کنار گذاشته می‌شود. قیمت/موجودی تازه در registry محصول بر snapshotهای قبلی اولویت می‌گیرند.

مبلغ هر خط و جمع در CartPage/Drawer از cart API است؛ مقدار نامعلوم صفر نمایش داده نمی‌شود. کالای ناموجود باقی و قابل حذف است. ذخیره، خطا، کمبود و مبلغ نامعتبر ادامهٔ خرید را می‌بندند؛ retry داخل خود drawer نیز وجود دارد. علاقه‌مندی/مقایسه مستقل از وضعیت سرویس هویت بازیابی می‌شوند و فقط شناسه‌های قبلی مرورگر را نگه می‌دارند.

## انتقال انتخاب‌های پیشین

نسخهٔ قبلی فقط در `sayman:shop:v1` اقلام را داشت. API mode آن نسخه را بی‌صدا پاک یا با سبد عضو جایگزین نمی‌کند. اعلان «بررسی و انتقال»، فهرست انتخاب با وضعیت فعلی کالا را باز می‌کند. انتقال انتخاب‌های قدیمی برای تنوع مشترک، تعداد بیشتر را نگه می‌دارد؛ این قرارداد با ادغام مهمان/عضو که تعدادها را جمع می‌کند متفاوت است. تعداد/مبلغ/موجودی در سرور دوباره بررسی می‌شوند.

فقط پس از پاسخ موفق PUT، شناسه‌های انتخاب‌شده از فهرست انتقال باقی‌مانده کم می‌شوند. ناموجود، انتخاب‌نشده، خطا و تعارض باقی می‌مانند؛ فایل اولیهٔ localStorage دست‌نخورده است. مجموعِ بیش از۶۴ تنوع بدون truncation رد و پیام حد نمایش داده می‌شود. تکرار پس از پاسخ گمشده یا شکست ذخیرهٔ marker، به‌دلیل merge از نوع maximum تعداد را دوباره زیاد نمی‌کند. دادهٔ جدید عضو و قیمت/موجودی/توکن در این marker ذخیره نمی‌شود.

## پذیرش مرورگر این برش

از build دقیق production در دامنهٔ مستقل `sayman-ui.localhost:3105`، API واقعی5181 و دیتابیس موقت `SaymanTest_Ui_*` استفاده شد. انتخاب‌های قدیمی با خود UI preview ساخته و پس از جابه‌جایی همان origin به API از UI منتقل شدند؛ state مرورگر تزریق نشد. حساب مشتری موقت واقعی ASP.NET Identity بود؛ حساب مدیر مالک یا MFA او استفاده نشد.

۱۱ بررسی دستی CUA در `artifacts/checks/server-cart-ui.json`: انتقال دو انتخاب قدیمی، PUT/تعداد و reload، ورود و ادغام، حفظ سبد در تغییر زبان، خروج و جداسازی مهمان، ادغام دوبارهٔ مهمان تازه بدون اثر تکراری، همگامی تعداد و خروج در دو تب، timeout و بازیابی داخل drawer، و موبایل بدون سرریز افقی. در fault test فقط process همین API موقت pause/resume شد؛ سبد پنج‌قلمی حفظ، checkout بسته و پس از retry همان مقدار SQL برگشت. override درخواست‌شده390×844، عرض client و scroll هر دو375 بود و override reset شد.

شاهدها: `sayman-server-cart-en.png`، `sayman-server-cart-mobile.png` و `sayman-cart-connection-recovery.png` در artifacts/screenshots. تب‌ها و دو process QA بسته و دیتابیس/کلید/credential تولیدشدهٔ خود harness حذف شدند. هیچ credential در گزارش یا تصویر نیست. SQL fixture نیز repository واقعی Data Protection را به پوشهٔ تست محدود می‌کند و مسیر آن را assert می‌کند؛۳۱ SQL دوباره پاس شد. طرح تست مستقل در `backend/tests/Shop.UiHarness` و runnerها در scripts قرار دارند و وارد image محصول نمی‌شوند.

main روی3000 با API5080 اجراست. در مرورگر اصلی، علاقه‌مندی و مقایسه و انتخاب‌های قدیمی حفظ و دکمهٔ انتقال آماده دیده شدند؛ سبد پیشین مالک خودکار منتقل نشد. پنل/MFA مالک همچنان handoff جدا دارد. نصب دستگاه/Push، پذیرش نهایی Linux x64، بار، callback واقعی، QA کامل پنل و سیاست نگهداری داده باقی‌اند.

هفت بررسی HTTP نهایی هویت نیز با `python3 scripts/smoke-customer-auth.py` موفق‌اند: refresh بدون session، logout بدون session، me بدون bearer، بسته‌بودن setup در BFF مشتری، سقف body، Origin نامعتبر و حذف header/cookie پنل. در این بررسی، نگاشت اشتباه401 خالی به503 کشف و اصلاح شد؛ challenge بدون body اکنون همان401 را حفظ می‌کند. گزارش `customer-auth-proxy.json` هیچ credential واقعی ندارد. runner محلی API mode، origin ثابت127.0.0.1:3000 را در صورت نبود تنظیم می‌گذارد؛ مقدار صریح کاربر حفظ می‌شود. محیط استقرار همچنان به origin واقعی نیاز دارد.

به‌روزرسانی بعدی: quote سروری و رابط checkout محاسبه‌ای در [CHECKOUT-QUOTES.md](CHECKOUT-QUOTES.md) پیاده و پذیرفته شده‌اند؛ سفارش و اتصال رزرو هنوز باقی‌اند. شمارش۳۱/۱۱۷/۶۲ بالا شواهد همان برش سبد است؛ آخرین شمارش در STATUS است.
