# رزرو موجودی

این برش، قرارداد داخلی Inventory برای سفارش آینده است. endpoint عمومی رزرو، سبد سروری، سفارش و پرداخت متصل هنوز ساخته نشده‌اند. هیچ رزروِ قابل خرید از شناسه‌ها یا تعداد ارسالی مرورگر بدون اعتبارسنجی سفارش ساخته نمی‌شود.

## داده و مالکیت

Inventory مالک `Reservations`، `ReservationItems`، `ReservationEvents`، موجودی و دفتر تغییر است. migration چهاردهم `StockReservations` و SQL idempotent در `backend/sql/inventory.sql` قرار دارند. Sales تنها `IStockReservations` در SharedKernel را مصرف خواهد کرد؛ context ماژول دیگری در Inventory مصرف نمی‌شود.

هر رزرو یک owner، OrderId و RequestId دارد. OrderId و RequestId به UUID بدون خط‌تیره نرمال می‌شوند. ترکیب owner/request و نیز OrderId یکتا هستند. شناسهٔ رزرو از owner/request به‌شکل پایدار ساخته می‌شود تا قفل آن پیش از هر خواندن SQL مشخص باشد؛ این شناسه مجوز دسترسی نیست و تمام عملیات مالک را بررسی می‌کنند. owner و actor شناسهٔ داخلی ASCII تا۶۴ حرف هستند؛ PII و اطلاعات پرداخت در رویداد ذخیره نمی‌شود.

۱ تا۶۴ تنوع متمایز، مقدار۱ تا۱٬۰۰۰٬۰۰۰ و عمر۱ تا۶۰ دقیقه مرز فنی فعلی‌اند. ترتیب اقلام و حروف شناسهٔ تنوع قبل از hash نرمال می‌شوند؛ hash شامل order، اقلام و مدت است. replay همان ID، وضعیت و مهلت اصلی را برمی‌گرداند؛ تغییر payload تعارض است. کلید تازه برای همان سفارش، حتی بعد از انقضا، رزرو تازه نمی‌سازد. سیاست تجاری مدت رزرو هنوز تأیید نشده؛ caller معتبرِ سرور مدت را تعیین می‌کند و مرورگر اختیاری برای تمدید ندارد.

## وضعیت‌ها

| حالت و درخواست | نتیجه و اثر انبار |
|---|---|
| ایجاد معتبر با موجودی کافی | Active؛ فقط Reserved زیاد می‌شود |
| Active قبل از انقضا + Allocate | Allocated؛ موجودی فیزیکی تغییر نمی‌کند |
| Active در/پس از مهلت | Expired؛ Reserved آزاد می‌شود، تخصیص دیررس موفق نمی‌شود |
| Active یا Allocated + Release | Released؛ Reserved کم می‌شود؛ خروج فیزیکی ثبت نمی‌شود |
| Allocated + Fulfill | Fulfilled؛ Reserved و OnHand کم و ledger خروج یک بار ثبت می‌شود |
| تکرار همان تغییر | همان نتیجه؛ اثر انبار/ledger/رویداد تکرار نمی‌شود |
| Fulfilled + Allocate تکراری | Fulfilled حفظ می‌شود |
| Fulfilled + Release یا Active + Fulfill | تعارض وضعیت؛ بدون تغییر |

Allocated پس از تأیید پرداخت/اعتبار معتبر، تحت مهلت رزروِ موقت منقضی نمی‌شود. این قرارداد خودش هیچ تأیید مالی تولید نمی‌کند. پس از ارسال، مرجوعی باید گردش و رسید انبار جدا داشته باشد؛ Release جای مرجوعی نیست. پرداختِ دیررس باید نتیجهٔ Expired را در Sales/Payments به مسیر تعیین‌تکلیف مالی ببرد؛ آن مسیر هنوز پیاده نشده است.

Read فقط مالک را می‌خواند و Active گذشته از مهلت را Expired نمایش می‌دهد، بدون نوشتن. تا آزادسازی worker، شمار موجودی قابل فروش می‌تواند محافظه‌کارانه کمتر باشد؛ رزرو گذشته از مهلت قابل تخصیص نیست.

## تراکنش و همزمانی

فرمان مستقل یک ReadCommitted باز می‌کند؛ تراکنش والد ReadCommitted یا Serializable را join و هرگز commit نمی‌کند. caller پس از خطا باید scope/واحد کار را کنار بگذارد و تراکنش ریشه را rollback کند. اتصال مشترک چندماژولی فقط وظیفهٔ composition root آیندهٔ سفارش است.

قفل‌های transaction-owned SQL برای request، order و reservation و قفل سطر موجودی با `UPDLOCK,HOLDLOCK` استفاده می‌شوند. قفل سراسری برای همهٔ انبار وجود ندارد. تنوع‌ها با ترتیب ثابت خوانده می‌شوند؛ همهٔ اقلام پیش از تغییر شمارنده بررسی می‌شوند. اصلاح دستی موجودی نیز قفل write-intent را پیش از lookup idempotency می‌گیرد و اجازهٔ کاهش OnHand زیر Reserved ندارد. rowversion و محدودیت `0 <= Reserved <= OnHand` برقرارند.

زمان انتظار application lock ده ثانیه است؛ نتیجهٔ منفی تراکنش را rollback و تعارض قابل تکرار با همان requestId می‌دهد. طبق [مستند SQL Server](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-getapplock-transact-sql?view=sql-server-ver17)، شکست application lock الزاماً rollback خودکار ندارد؛ کد نتیجه را صریح بررسی می‌کند. deadlock SQL با1205، شامل wrapper محدود EF، در API به409 نگاشت می‌شود؛ retry خودکار چندمرحله‌ای مالی ساخته نشده است.

worker به‌طور پیش‌فرض هر دقیقه حداکثر۱۰۰ نامزد Active گذشته از مهلت را بررسی می‌کند. هر رزرو تراکنش کوتاه و قفل خودش را دارد؛ اجرای batch در تراکنش والد رد می‌شود تا خواندن فهرست نامزدها قفل طولانی نگیرد؛ چند worker می‌توانند رقابت کنند و فقط یک تغییر ثبت می‌شود. با `Inventory__ExpiryEnabled=false` غیرفعال می‌شود. اجرای یک batch دستی:

```sh
python3 scripts/backend-local.py --expire-stock-reservations
```

در backlog بزرگ، batchهای بعدی ادامه می‌دهند؛ ظرفیت و پایش انقضا هنوز باید در آزمون بار پذیرفته شوند. ردیف‌ها و رویدادها حذف نمی‌شوند. انقضا فقط اثر موجودی دارد؛ وضعیت سفارش/پیام‌رسانی/outbox برای اتصال بعدی باقی است.

## شاهد آزمون و کار باقی

۱۲ سناریوی تازه روی SQL Server واقعی: آخرین واحد و دو خریدار، replay همزمان/مدت ثابت/payload متفاوت، کمبود یک قلم و rollback کل سبد، اقلام با ترتیب معکوس، تخصیص و ماندگاری بعد از مهلت، ارسال دوباره بدون ledger تکراری، لغو Active/Allocated، دو worker منقضی‌کننده، رقابت انقضا/پرداخت دیررس، مالک نامعتبر/ارسال زودرس، مالکیت commit والد/خطای عمدی رویداد و جلوگیری از اصلاح موجودی رزروشده. همراه۱۰ تست پیشین، مجموع۲۲ SQL موفق‌اند. ۱۰ اعتبارسنجی بدون اتصال SQL نیز به مجموع۱۰۶ تست بک‌اند اضافه شدند.

این شاهد روی SQL محلی AMD64 با Rosetta است؛ Linux x64 نهایی و بار جدا باقی‌اند. UI تغییری نکرده است. سبد و ادغام مهمان، quote معتبر سرور، snapshot سفارش، پرداخت تأییدشده، تطبیق دیررس، ارسال، سریال/IMEI و حسابداری هنوز متصل نیستند. INV-01 و فاز۴ هنوز کامل نیستند.
