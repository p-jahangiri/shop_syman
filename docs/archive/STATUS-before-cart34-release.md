## SerialV2 و فرمان تخصیص؛ SQL و مرورگر دسکتاپ پذیرفته، منتشرنشده

`serial-allocation-acceptance.json` شاهد فعلی این برش است؛ اعداد و candidateهای بخش Foundation پیشین، تاریخچهٔ قبل از SerialV2/فرم‌اند. **۶۸۵/۶۸۵ واحد بک‌اند،۱۳/۱۳ SQL تازه و رگرسیون کامل۳۲۶/۳۲۶،۱۷۴/۱۷۴ پنل و۲۱۵/۲۱۵ فروشگاه موفق‌اند؛ صفر fail/skip.** build solution/SqlTests/UiHarness، typecheck و Vite ایزوله موفق‌اند. ۱۱ SQL تازهٔ SerialV2 و۲ migration به۳۱۳ پیشین افزوده شدند؛ ۹ واحد SerialV2 عدد۶۷۶ را به۶۸۵ رساندند. تغییرهای آخرِ متن/جای نوار بازیابی فقط typecheck/build و آزمون واقعی مرورگر گرفتند؛ آزمون mirror تازه ساخته نشد.

SerialV2 در `/api/admin/inventory/variants/{id}/serials/v2`، موجودی فیزیکی/رزرو سفارش/سهم تأمین/آزاد را مستقل می‌دهد؛ wrapper هر دستگاه claim فعال را صریح نشان می‌دهد. available، دستگاه محفوظ حتی منقضی ولی هنوز آزادنشده را حذف می‌کند. cursor نسخه۲ به Stock.Version مقید و صفحه۵۰تایی است؛ این read snapshot تاریخی چندصفحه‌ای نیست. reader نسخه۱ در سهم/claim فعال409 upgrade می‌دهد؛ mutation/history/receipt قدیمی حفظ‌اند و رگرسیون SQL آن‌ها پذیرفته است. پنل دو دستگاه محفوظ را نشان داد، دکمهٔ خروج هر دو بسته بود و فیلتر آزاد فقط دستگاه سوم را آورد.

فرم تخصیص به همان journal/قفل/مالک جاری متصل است: تمام خطوط پذیرش، مهلت UTC خالی تا اقدام صریح مدیر، دلیل، انتخاب دستی دستگاه و نسخه‌های Stock/unit؛ قیمت و مالک وارد body نمی‌شوند. receipt تاریخی پس از Released/Expired/Transferred احیا نمی‌شود. مرور مستقل دو جهتِ read ناسازگار را بست: Active فقط با summary همان ID/version، terminal فقط با null یا تخصیص دیگر معتبر است. دریافت موفق و discard خطای قطعی، candidate/picker/SerialV2 را تازه و تأیید/انتخاب/UUID فرم را reset می‌کنند. unknown قابل discard نیست. نوار فرمان و خطا داخل modal فقط یک بار render می‌شود؛ بازیابی پشت پنجره پنهان نمی‌ماند.
