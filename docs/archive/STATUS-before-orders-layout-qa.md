- backend سفارش موقت/رزرو/خالی‌کردن سبد اتمیک، snapshot، idempotency، مالکیت، لغو و worker انقضا؛ تنظیم مجوزدار و audit؛ quote تازه schema3 پیاده‌اند. سفارش پیش‌فرض خاموش و بدون درگاه همیشه پرداخت‌نشده است. هزینهٔ واقعی همچنان تعیین‌نشده؛ چک/پرداخت واقعی غیرفعال‌اند.
- فرم سفارش، نشانی فیزیکی ایران/دیجیتال بدون نشانی، سفارش‌های من، جزئیات/لغو، ورود با returnTo محدود و FA/EN در سورس وصل‌اند. پنل صفحهٔ lazy سفارش و تنظیم مدت/سقف رزرو دارد. در نتیجهٔ نامعلوم همان payload/UUID retry می‌شود؛ پاسخ خصوصی دیررس پس از logout کنار می‌رود. دادهٔ فرم فقط حافظه‌ای است.
- اجرای تازه۹۰ فروشگاه و۱۹۴ بک‌اند موفق؛ typecheck هر دو رابط و compile تست SQL/UiHarness با صفر warning/error موفق. build Vite جدا در `tmp/orders-admin-dist` موفق و dist زنده دست‌نخورده؛ chunk صفحهٔ orders حدود۱۵kB و chunk اصلی۵۱۳kB است، هشدار قبلی۵۰۰kB هنوز باز. build تازهٔ Next و QA مرورگر این برش **انجام نشده‌اند**.

## محیط فعلی و بازیابی

کمبود شدید فضای میزبان (۱۶۴ MiB) حین build Linux باعث I/O در Docker و اختلال SQL شد. cache توسعهٔ Next و bin تست‌های همین پروژه پاک شدند؛ سورس/کلید/گزارش/volume محفوظ ماندند. پس از فراهم‌شدن فضای میزبان (آخرین مشاهده حدود۱۸–۲۰ GiB)، Docker و SQL با volume موجود بازیابی شدند؛ Sayman برابر ONLINE و DBCC CHECKDB بدون repair و بدون خطا بود. API live/ready و کاتالوگ متصل دوباره200 هستند؛ گزارش `environment-recovery.json`.

cache پیش‌فرض BuildKit یک snapshot گمشده گزارش کرد و تغییر داده نشد. builder مستقل `sayman-build` در config ناشناس `tmp/docker-public`، با BuildKit رسمی digest ثابت و حافظه۲GiB ساخته شد؛ default کاربر تغییر نکرد. هر دو build Linux موفق شدند؛ سورس پیش از audit/رزرو با۹۶ تست Linux پاس شد. image موقت SDK آزمون پس از بررسی نبود مصرف‌کننده حذف شد و گزارش/cache اختصاصی باقی‌اند. حالت backend-test در wrapper اکنون cacheonly است تا image سنگین SDK دوباره import نشود. build runtime API به‌علت guard شروع نشد: فضای آزاد آخرین مشاهده۸٫۸GiB، حد شروع۱۰GiB. از `scripts/build-local-image.py ... --isolated` استفاده شود؛ حداقل۱۰GiB برای شروع و لغو خودکار همین build زیر۳GiB. این guard فقط فضای میزبان را می‌سنجد و جای پایش Docker/SQL نیست.

- تغییر مجاز مدیریت و AuditEvent در Serializable مشترک درخواست commit می‌شوند. connection فقط در همان فرمان مشترک است؛ خواندن عمومی و migrationها factory مستقل قبلی را دارند. Category/Inventory تراکنش والد را join می‌کنند. هیچ تنظیم محرمانهٔ اتصال ضعیف نشده و هیچ schema جدیدی لازم نیست.
- SQL: خطای عمدی audit در دیتابیس تست، برند/دسته/موجودی، ledger و rowversion را rollback کرد؛ موفقیت یک رویداد و stale/read هیچ رویداد موفقیت نوشتند. چهار مورد تازه و شش مورد قبلی، مجموع۱۰ SQL موفق. ۹۶ تست غیرSQL هم پاس‌اند؛ گزارش‌های backend-tests.log و sql-tests.log.
- API تازه روی5080 فعال شد؛ readiness و metadata200 و audit ناشناس401. Linux۹۶ قبلی پیش از این تغییر audit بوده و آخرین سورس audit هنوز داخل Linux دوباره اجرا نشده است؛ guard ظرفیت برای imageها برقرار است.
- audit قبل/بعد دامنه، امنیت شکست‌ها، کارکنان/بازیابی MFA و load همچنان باقی‌اند؛ برش جدید در ARCHITECTURE/API شرح داده شده است.

## رسانه و ورود مدیر

- reconciliation: Staged/Failed حداقل۲۴ساعته، cooldown یک‌ساعته، lease پنج‌دقیقه‌ای با rowversion، حذف bounded خروجی‌های همان ID و حفظ ردیف با Purged. Ready هرگز هدف نیست. worker فقط با `Media__CleanupEnabled=true`، پنج دقیقه پس از startup و سپس ساعتی؛ فرمان `--reconcile-public-images` برای اجرا دستی. scanner/storage واقعی هنوز پذیرش ندارند.
- تست hostها از تنظیمات واقعی scanner/storage/worker جدا شدند؛ آزمایش با Media محیط فعال هم موفق است. انتخاب adapter پس از بارگذاری نهایی config انجام و guard Production هنگام startup حفظ می‌شود؛ دو تست ویژه این مرز را می‌سنجند.
- پنل پس از رمز دیگر خودکار setup را نمی‌خواند؛ دکمهٔ صریح «راه‌اندازی Authenticator»، نام حساب واقعی و نرمال‌سازی ارقام فارسی/عربی کد اضافه شد. tab قبلی پس از تداوم محیط موجود نبود؛ تب تازه3173 در مرحلهٔ آغاز MFA به مالک واگذار شد (بدون تولید/نمایش مجدد کلید توسط عامل). تصویر امن `sayman-admin-mfa-start.png`.
- مرورگر API+SQL: فیلتر۵۱۲ به یک Samsung S25/v2-black رسید و پس از تغییر زبان همان ID/تنوع حفظ شد؛ گالری تنها یک تصویر واقعی seed داشت. عکس `sayman-sql-filter-en.png`. mutation پنل هنوز پس از MFA مالک باید بررسی شود.

## query کاتالوگ در سمت سرور

- API جست‌وجوی صفحه‌بندی‌شده، فیلتر تایپ‌دار، دریافت filters، lookup حداکثر ۶۴ شناسه و bootstrap با `metadataOnly=true` اضافه شد. قیمت/موجودی/ویژگی روی همان تنوع اعمال می‌شوند و ترتیب پایدار است.
- Inventory مالک قرارداد view خواندنی `AvailableStockV1` است؛ Catalog فقط DTO keyless آن را می‌خواند و DbContext ماژول دیگر را مصرف نمی‌کند. migration و SQL این view اعمال و query آن در تست SQL واقعی بررسی شد.
- فیلد مشتق‌شدهٔ جست‌وجوی نام/برند/SKU با NFKC و فارسی در ذخیره ساخته می‌شود. migration، repair دسته‌ای و readiness/search برابر 503 تا پایان repair اضافه شد. این مسیر جای موتور جست‌وجو/غلط املایی/مترادف را نمی‌گیرد.
- root فروشگاه فقط metadata با `products: []` می‌گیرد؛ خانه بلوک‌های محدود، محصول lookup همان slug و حداکثر چهار مرتبط، و کاتالوگ فقط همان صفحه را SSR می‌کنند. فیلتر/مرتب‌سازی/صفحه در URL می‌مانند؛ انتخاب ۵۱۲ گیگابایت و حفظ همان تنوع پس از تغییر زبان در مرورگر بررسی شد.
- BFF عمومی search/filters/lookup/facet-values ورودی، اندازهٔ body و پاسخ را اعتبارسنجی می‌کند؛ no-store است و cookie/Authorization را به API منتقل نمی‌کند. خطای API به fixture برنمی‌گردد. پیشنهاد جست‌وجو و تب دستهٔ خانه با درخواست محدود و قابل لغو خوانده می‌شوند.
- سبد/علاقه‌مندی/مقایسه فقط ID/تعداد ذخیره می‌کنند؛ lookup دسته‌های حداکثر ۶۴تایی قبل از hydrate انجام می‌شود. خطای میانی اطلاعات ذخیره‌شده را دست‌نخورده می‌گذارد؛ بازیابی با retry و reload در مرورگر دیده شد. محصولات بازشده فقط در scopeهای حافظه و انتخاب‌های ذخیره‌شده می‌مانند.
- sitemap و DTO آفلاین از مسیر مستقل snapshot کامل در سمت سرور استفاده می‌کنند؛ محدودسازی query آن دو در سرور و اندازه‌گیری بار هنوز باقی است. جزئیات در `docs/CATALOG-QUERY.md`.

## جست‌وجو و صفحه‌بندی مقدار ویژگی

- `POST /api/catalog/{locale}/facet-values` و BFF آن برای پنج نوع ویژگی آماده‌اند؛ pageSize پیش‌فرض ۲۰/حداکثر ۶۰، query تا ۱۰۰ حرف/۸ واژه و حداکثر ۲۰ انتخاب. فهرست اولیه فقط ۲۰ مقدار و total/truncated دارد؛ مقدارهای بعدی دیگر به سقف ۶۰ محدود نمی‌شوند.
- عنوان انتخاب‌های بیرون صفحه/نتیجهٔ جست‌وجو جدا دریافت و ثابت نمایش داده می‌شود. انتخاب‌های URL در تغییر زبان حفظ می‌شوند؛ خطا و retry، لغو درخواست قبلی و جلوگیری از عبور انتخاب‌ها از حدود API در UI وجود دارد.
- نام گزینه و متن ویژگی دو زبان هنگام ذخیره با همان NFKC/ی/ک/ارقام نرمال می‌شوند. فیلد داخلی FacetSearch در JSON خروجی نیست. migration یازدهم `FacetSearchFields` و SQL Catalog اعمال شده‌اند؛ repair قبلی در batchهای ۲۵۰تایی این فیلدها را هم پر می‌کند و readiness/search تا پایان repair خطا می‌دهند.
- query متن/عدد فقط مقدار مؤثر تنوع فعال یا مقدار ارث‌رسیده را می‌بیند. خواندن metadata دیگر تمام گزینه‌ها را eager-load نمی‌کند؛ نمایش صفحهٔ محصول فقط گزینه‌های واقعاً مصرف‌شده و اعتبارسنجی جست‌وجو فقط IDهای انتخاب‌شده را می‌خواند.
- مرورگر محیط موقت با ۸۳ گزینه: صفحهٔ پنجم، انتخاب ۵۱۲، برگشت صفحه، تغییر زبان و جست‌وجوی ۲۵۶ با حفظ انتخاب قبلی بررسی شد. این API نمونهٔ صریح، مستقل از SQL بود و پس از آزمون همراه تب و process خودش بسته شد. عکس/محدودیت در `CATALOG-QUERY.md`.

## API، SQL و پنل

- solution ماژولار .NET 10 اکنون build می‌شود؛ EF Core 10.0.12، lockfileهای NuGet و نسخهٔ اصلاح‌شدهٔ Pkcs 10.0.13. هشدار آسیب‌پذیری سرکوب نشده است.
- Catalog: دستهٔ درختی/برند/دو ترجمه، Text/Number/Bool/Select/MultiSelect رابطه‌ای، قواعد دسته برای فرم/فیلتر/مشخصات/مقایسه، تنوع/SKU/قیمت/گارانتی، روش خرید و طرح اختصاصی، تاریخچهٔ قیمت و rowversion.
- Inventory: موجودی فیزیکی/رزروشده، دفتر تغییر، اصلاح با دلیل/عامل/requestId، تراکنش Serializable و نسخه. رزرو داخلی، انقضا/آزادسازی/تخصیص/ارسال و ledger تراکنشی آماده و در SQL آزموده‌اند؛ اتصال سفارش، سریال/IMEI و حسابداری کامل هنوز باقی‌اند.
- Payments/Credit: ماه/فاصله/افزوده/پیش‌پرداخت basis point، محدودیت مبلغ/دسته و واحد گردکردن ۱ یا ۱۰ ریال از پنل قابل تنظیم‌اند. نمایش و ورودی تومان یک رقم اعشار را دقیق حفظ می‌کند؛ quote نمونه درصد با دو رقم اعشار و فاصلهٔ چندماهه را می‌پذیرد، پیش‌پرداخت از اصل بیشتر نمی‌شود و باقیمانده به چک آخر می‌رود. quote معتبر سروری، تنظیم هزینه و رابط محاسبه‌ای آماده‌اند؛ ثبت سفارش و تأیید/وصول چک هنوز وجود ندارند؛ نرخ و سیاست واقعی تأیید نشده است.
- CMS: draft، انتشار و revision/بازگردانی، محتوای دو زبانه، بلوک whitelist، تاریخ UTC و رنگ با اعتبارسنجی خوانایی. preview خصوصی draft و صفحه‌ساز کامل/بلاگ باقی‌اند.
- Identity: ASP.NET Identity، رمز هش‌شده، lockout/rate limit، JWT، refresh هش‌شده و چرخشی، جداسازی cookie/Origin پنل، policyهای مجوز، MFA با کلید رمز‌شده و counter یک‌بارمصرف. آزمون TOTP با بردارهای RFC پاس شده؛ جریان SQL واقعی با سناریوی جدا تأیید شد؛ QA حساب اصلی پنل باقی است. key ring محلی باید حفظ شود؛ Production به certificate و محل پایدار کلید نیاز دارد.
- پنل مستقل Vite: فرم دوزبانهٔ کالا و تنوع، دسته و ویژگی پویا، برند، انبار، روش خرید/چک، CMS/منو/بلوک/تنظیم برند، رویداد مدیریت و ورود Authenticator. تست مرورگر فعلاً فقط صفحهٔ ورود/اعتبارسنجی و موبایل را پوشش داده؛ گردش ذخیرهٔ واقعی هنوز تأیید نشده است.
- هفده migration برای هفت schema و هفت SQL idempotent در `backend/sql` تولید شده‌اند. IdentityAuthenticatorReplay فیلدهای اولیهٔ استفاده‌نشده را به counter تبدیل می‌کند؛ migrationها و seed صریح توسعه اکنون روی SQL محلی با موفقیت اعمال شده‌اند. migrationهای اخیر CatalogSearchFields، InventoryPublicAvailability، ChequeRoundingUnit، FacetSearchFields و PublicCatalogueImages و PublicImageCleanupLeases و StockReservations و ServerCarts و CheckoutQuotes و CheckoutChargePolicies هستند.
- runtime پنل و Dockerfileهای API/پنل و Compose آماده‌اند؛ digestهای .NET رسمی ثابت‌اند. stage آزمون Linux با۹۶ موفق ساخته شد؛ image runtime API و image پنل هنوز اجرا نشده‌اند.
