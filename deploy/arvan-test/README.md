# نسخهٔ آزمایشی Docker سایمان روی آروان

این Compose برای اجرای Development روی سرور اختصاص‌یافتهٔ آزمایش است. API و SQL فقط در شبکهٔ Docker هستند. فروشگاه و پنل روی loopback میزبان به‌ترتیب ۱۳۰۰۰ و ۱۳۱۷۳ در دسترس‌اند. پروفایل `edge` با گواهی نصب و فهرست دسترسی IP آزمایشگر فعال می‌شود.

## آماده‌سازی

بستهٔ سورس را با `deploy/package-production.py` صادر کنید. برای ارسال به Linux از tar بدون AppleDouble استفاده کنید و SHA-256 آرشیو را در مقصد بررسی کنید. تصاویر API، فروشگاه و پنل را برای `linux/amd64` بسازید. در build پنل، `VITE_STOREFRONT_URL` را با مسیر دسترسی واقعی هماهنگ کنید. برای تونل از `http://127.0.0.1:13000` استفاده کنید.

فایل‌های Compose و Nginx را در `/opt/sayman/shared/deploy` قرار دهید و با استفاده از `deploy.env.example`، `deploy.env` را بسازید. Seed پروژه را با مجوز خواندن برای کانتینر در `/opt/sayman/shared/development.json` قرار دهید. روی دیتابیس تازه، `sudo bash first-install.sh` مراحل ساخت کلید، دیتابیس، بکاپ، Seed و راه‌اندازی داخلی را اجرا می‌کند.

برای Compose از فایل خصوصی `deploy.env` شامل نام تصویرها و متغیرهای `SAYMAN_SHARED`، `SHOP_ORIGIN`، `ADMIN_ORIGIN`، `SHOP_DOMAIN`، `ADMIN_DOMAIN` و `TESTER_IP` استفاده کنید. در پوشهٔ مشترک میزبان:

- `sql.env` رمز تازهٔ `MSSQL_SA_PASSWORD` را دارد. حجم `sql-data` پایدار است.
- `runtime.env` رشتهٔ اتصال حساب محدود دیتابیس، `Auth__SigningKey` و `DataProtection__CertificatePassword` را دارد. هر رمز و کلید جداگانه تولید می‌شود.
- `identity-keys` و گواهی مستقل `identity.pfx` برای UID برنامهٔ API خواندنی‌اند. فایل گواهی و کلیدهای برنامه با TLS درگاه متفاوت‌اند.
- `development.json` از `backend/Seed/development.json` می‌آید.

بعد از سلامت SQL، دیتابیس Sayman و حساب runtime محدود به خواندن و نوشتن همان دیتابیس را بسازید. بکاپ اولیه را با `BACKUP … WITH COPY_ONLY, CHECKSUM` و `RESTORE VERIFYONLY … WITH CHECKSUM` بگیرید. برای نصب نخست، `--seed-dev` را یک‌بار در کانتینر API با اتصال موقت migration و `Bootstrap__AdminPassword` تازه اجرا کنید. مقادیر موقت در محیط کانتینر دائم قرار نمی‌گیرند. بعد از بکاپ دادهٔ نمونه، Compose را بالا بیاورید و سلامت API، صفحهٔ فروشگاه و پنل را بررسی کنید.

## دسترسی از طریق تونل

```sh
ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:13000:127.0.0.1:13000 \
  -L 127.0.0.1:13173:127.0.0.1:13173 root@94.101.186.45
```

با تنظیم originهای loopback در `deploy.env` و در زمان بازبودن تونل، [فروشگاه](http://127.0.0.1:13000/fa) و [پنل](http://127.0.0.1:13173/) از همان دستگاه باز می‌شوند. مدیر MFA را در اولین ورود در پنل تکمیل می‌کند.

برای اجرای HTTPS روی یک IP، پنل از پورت ۴۴۳ و فروشگاه از `SHOP_TLS_PORT` (پیش‌فرض ۸۴۴۳) استفاده می‌کند. هر دو متغیر `SHOP_DOMAIN` و `ADMIN_DOMAIN` را به IP میزبان تنظیم کنید؛ `SHOP_ORIGIN` شامل پورت فروشگاه است و `ADMIN_ORIGIN` همان HTTPS روی ۴۴۳. هر دو پورت باید از IP آزمایشگر قابل دسترس باشند. اگر نشانی قبلی فروشگاه دارید، `SHOP_LEGACY_DOMAIN` آن را به نشانی جدید هدایت می‌کند؛ برای هدایت از HTTPS، گواهی باید نام قبلی را هم پوشش دهد.

گواهی و کلید همین نصب را در `SAYMAN_TLS_DIR` قرار دهید و برای پروفایل HTTPS مقدار `SAYMAN_SECURE_AUTH_COOKIES=true` بگذارید. برای تونل HTTP، مقدار پیش‌فرض `false` است. گواهی عمومیِ نصب آزمایشی را در صورت خصوصی‌بودن صادرکننده جداگانه به دستگاه تست منتقل کنید. Nginx فقط کوکی‌های همان رابط را به سرویس مربوط می‌فرستد؛ جداسازی کامل کوکی در مرورگر به نام‌های میزبان جداگانه نیاز دارد.

اگر گواهی معتبر آماده نیست و پنل و فروشگاه روی یک IP هستند، `SHOP_HTTP_BROWSE=true` مرور عمومی فروشگاه را روی پورت ۸۰ فعال می‌کند. Nginx فقط صفحه‌ها و دارایی‌های عمومی و جست‌وجوهای خواندنی کاتالوگ را می‌پذیرد. کوکی و هدر احراز هویت به فروشگاه ارسال نمی‌شوند. پنل، ورود و خرید از مسیر HTTPS کار می‌کنند. پس از صدور گواهی معتبر، مقدار را به `false` برگردانید. برای نصب PWA، صفحهٔ فروشگاه باید با همان گواهی معتبر از HTTPS باز شود.

برای IP عمومی، Let's Encrypt گواهی رایگان کوتاه‌عمر صادر می‌کند. مسیر `/.well-known/acme-challenge/` باید از اینترنت روی TCP ۸۰ پاسخ دهد و کاربر Nginx باید فایل چالش را از `acme-webroot` بخواند. صدور را ابتدا روی staging امتحان کنید. هنگام نصب گواهی معتبر، تمدید خودکار و reload Nginx را نیز بررسی کنید. [راهنمای گواهی IP](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability/)

## انتشار نسخه با تگ

تغییرات مجاز را به شاخهٔ `codex/arvan-test-deploy` بفرستید. یک تگ جدید مانند `test-v0.1.1` روی commit همان شاخه بزنید و تگ را push کنید. workflow مستقل آزمون، هر سه تصویر را روی Runner میزبانی‌شدهٔ GitHub می‌سازد. کش هر برنامه در GHCR جداست. ماشین آروان فقط digestهای نسخه را دریافت می‌کند و روی آن build انجام نمی‌شود.

- متغیر `ARVAN_TEST_STOREFRONT_URL` را به origin HTTPS فروشگاه همان نصب، با پورت در صورت استفاده از ۸۴۴۳، تنظیم کنید. پنل هنگام build همین نشانی را می‌گیرد.
- Runner سرور را با کاربر مستقل و label اختصاصی `arvan-test-deploy` به همان مخزن خصوصی ثبت کنید. Runner عضو گروه Docker نیست.
- روی هر میزبان `compose.yaml`، قالب Nginx و `deploy.env` را در `/opt/sayman/shared/deploy` با مالک root قرار دهید. مسیر گواهی در `SAYMAN_TLS_DIR` تعیین می‌شود. دادهٔ نمونه در Git نسخه‌بندی می‌شود و volume، backup و کلیدها روی میزبان می‌مانند.
- `ARVAN_TEST_AUTO_DEPLOY` پس از تأیید دسترسی محدود فعال می‌شود. نسخهٔ root-owned فایل `release.py` در `/usr/local/sbin/sayman-arvan-release` نصب می‌شود. قاعدهٔ sudo با SHA-256 همین فایل، `NOSETENV` و فهرست آرگومان خالی به Runner دسترسی می‌دهد. در این میزبان، `ARVAN_TEST_SUDO_PROVIDER=/usr/bin/sudo.ws` است و سیاست digest در `/etc/sudoers.sayman-ws` نگه‌داری می‌شود. sudo پیش‌فرض سرور مستقل است. هنگام به‌روزرسانی فرمان، SHA جدید را هم از نشست root در همان سیاست ثبت و با `visudo.ws` بررسی کنید.
- فرمان، commit و سه digest محدودهٔ مخزن را کنترل می‌کند، بکاپ و migration را انجام می‌دهد و بعد از بررسی سلامت نسخه را ثبت می‌کند. لاگ‌ها چرخشی‌اند و تصاویر نسخهٔ جاری و یک نسخهٔ موفق پیش از آن نگه داشته می‌شوند. حجم دیتابیس و بکاپ‌ها از پاک‌سازی تصویر جدا هستند.

برای نصب مشابه، گواهی و IP مجاز را مستقل بسازید و نام‌های میزبان را تغییر دهید. اگر نصب هم‌زمان روی میزبان دیگری لازم است، label و مقصد workflow را هم جدا کنید تا هر تگ فقط روی میزبان موردنظر اجرا شود.
